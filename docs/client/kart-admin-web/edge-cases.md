# Edge Cases: kart-admin-web

## Edge Case: Concurrent Support Agents Double-Approving the Same Refund Request

- **What happens:** Two Support Agents (or a Support Agent and an Admin) open the same `ReturnRequest` from the Refund Requests queue while it is still `Requested`, and both click Approve within moments of each other.
- **Why it happens:** `kart-admin-web` is a thin, fan-out client with no domain logic of its own (`architecture.md` Boundary Rationale) — it holds no lock on a queue item, and the real-time queue feed (WS/SSE) is explicitly "optional at launch," not adopted (`architecture.md` Dependencies table). Without it, two agents' queue views can go stale relative to each other between page-load and click, and the actual state-transition guard (`Requested → Approved`) lives entirely in `kart-order-service`/`kart-payment-service` (`checkout-and-refunds.md` §B.4-B.5), not in this app.
- **Solutions available (3):** Rely entirely on backend optimistic concurrency on the `ReturnRequest` transition — the losing submit is rejected with an "already resolved" response the client surfaces as a friendly error + auto-refresh · Client-side soft-lock ("being reviewed by X," visible to other viewers) that doesn't block the backend transition, only warns · Adopt WS/SSE-driven live queue updates so a second viewer sees the item resolve and its Approve control disable before they can click
- **Decision:**
  - Chosen: Backend optimistic concurrency (already required server-side regardless) plus a friendly "already resolved by <principal>, refreshing" client message — no client-side lock, no WS/SSE adoption for this feature alone.
  - Why: Matches this app's stated thin-client boundary (`architecture.md`) — the state-transition invariant has to exist in `kart-order-service` either way, so the client's only job is to present that rejection well; `architecture.md` already scopes real-time push as add-only-when-a-concrete-workflow-needs-it, and a same-request double-click is rare enough (human-paced, low-volume internal queue per §3.3) not to justify standing up push infrastructure just for this.
  - Trade-off accepted: A Support Agent can waste a click and see a same-request-already-approved error instead of an ideally pre-emptive greyed-out control; the queue list can transiently show already-resolved items until the next poll/refresh.
- **Status:** Resolved.

## Edge Case: Idle-Timeout Warning Countdown Racing an In-Flight Refund-Approval Submit

- **What happens:** The 60-second idle-timeout warning modal (`security.md` §2.2) fires while a Support Agent's Approve click on a refund request is still in flight (slow network/backend); it's unclear whether idle logout should pause/ignore the in-flight submit or let it race the revocation that fires "the moment idle logout fires" (`security.md` §2.2's enforcement note).
- **Why it happens:** `security.md` §2.2 specifies the idle-timer, warning-popup, and server-side revocation-on-logout mechanics in general terms but never addresses what happens to a mutating request already in flight at exactly that boundary — a gap the spec's own scope (session lifecycle) doesn't cover, and money-moving refund approval (§3.3) is exactly the class of action where an ambiguous outcome (did the refund happen or not?) is costly.
- **Solutions available (3):** Treat any outstanding mutating request as activity — pause/reset the idle countdown while a write is in flight, resume idle-counting only after the response lands · Let the countdown and the in-flight request race independently, relying on the platform-wide mandatory-`Idempotency-Key` convention (`checkout-and-refunds.md` §A.2, applied to every money-moving POST) so a post-logout retry after re-auth is safe · Block the Approve control entirely during the last 60 seconds of the idle countdown, forcing "Stay signed in" first before any submit is allowed
- **Decision:**
  - Chosen: Pause the idle timer while a mutating request is outstanding (treat it as activity), with the existing idempotency-key convention as a safety net for the residual case where the warning/logout already fired before a request started.
  - Why: An agent mid-submit is by definition actively working, not idle — timing out under them is a false-positive idle detection, not a security win; the platform already has an idempotency-key mechanism for exactly this class of "was it applied or not" ambiguity, so pausing the timer is a low-cost improvement layered on an existing safety net rather than a new mechanism.
  - Trade-off accepted: A stuck/hung request can hold the idle timer open indefinitely unless paired with a client-side request-timeout ceiling (not fixed by this pass) — without one, a hung request becomes an unintended way to defeat the idle policy.
- **Status:** Resolved.

## Edge Case: Admin's Federated Session Hits Its 24-Hour Absolute Cap Mid-Task With No Warning

- **What happens:** An Admin's SSO-federated session reaches its 24-hour absolute cap (no sliding extension, `security.md` §1/§2.2) while actively mid-task — e.g., partway through a multi-step permission-grant edit or a catalog bulk operation — and is force-logged-out with zero advance notice, unlike the idle-timeout path which gets a 60-second warning popup.
- **Why it happens:** `security.md` §2.2's warning-popup row is scoped only to idle-timeout logout; the absolute-lifetime row has no equivalent warning mechanism specified. Federated refresh tokens have "no sliding extension" by design (§1), and an actively-working Admin never trips the idle timer (by definition not idle), so the hard 24-hour wall can be hit with no prior signal at all.
- **Solutions available (3):** Add a distinct one-time advance warning (e.g., ~5 minutes before the absolute cap) telling the Admin to finish/save before forced logout, separate in copy from the idle-timeout modal since "Stay signed in" isn't a valid action here · Accept the hard cliff as inherent to "no sliding extension" and instead invest in autosave/resumable multi-step forms so sudden logout loses nothing · Silently attempt a transparent re-federation redirect at the cap boundary
- **Decision:**
  - Chosen: Add a distinct advance-warning modal ahead of the absolute cap, plus client-side autosave/draft-resilience for genuinely multi-step Admin forms (permission-grant edits, bulk catalog operations) as a second line of defense.
  - Why: The 24-hour figure itself is correct and not up for re-litigation (it inherits Identity's own federated cap verbatim, `security.md` §1) — but the complete absence of any warning for that specific path is a gap `security.md` §2.2's own table left open by scoping "warning popup" to idle-timeout only; a heads-up before an unavoidable hard logout costs nothing and doesn't compromise the no-sliding-extension guarantee.
  - Trade-off accepted: The warning is best-effort UX only — an Admin deep in an uninterruptible action (e.g., a submit already in flight) when the warning fires can still lose unsaved work, since the cap genuinely cannot be extended; silent re-federation was rejected outright as it would defeat the entire point of a hard, non-sliding cap.
- **Status:** Resolved.

## Edge Case: Support Agent's Refund-Approval Cap Changes Between Viewing and Approving

- **What happens:** A Support Agent opens a Refund Request whose amount sits within their per-order refund cap at render time (Approve renders enabled, per §3.3); before they click, an Admin edits/lowers that Agent's grant via Permission-grant management (§3.4); the Agent then clicks Approve on an amount now above their (new) cap.
- **Why it happens:** `requirement-spec.md` §5 states category/cap-gated controls are "UX convenience, not the enforcement point," rendered from the grant snapshot fetched at page-load/queue-render time — nothing re-fetches the cap between render and click. `kart-admin-service`'s grant table (`kart-admin-service/edge-cases.md`'s concurrent-editing and stale-permission edge cases) can be edited by an unrelated Admin action at any moment, so render-time and click-time are never guaranteed to see the same grant.
- **Solutions available (3):** Submit anyway and let the backend cap check reject the now-over-cap request, surfacing the same "Admin-escalation-required" messaging §3.3 already defines for an over-cap amount at request time, just discovered post-click · Re-validate the Agent's live cap immediately before enabling the Approve click (a just-in-time grant check) rather than trusting the render-time snapshot · Poll/subscribe to grant changes for the current principal and proactively re-render the queue if the viewer's own grant changes while it's open
- **Decision:**
  - Chosen: Server-side rejection with the existing "Admin-escalation-required" messaging surfaced post-click; no proactive re-fetch or live subscription added.
  - Why: `requirement-spec.md` §5 already establishes every write control here as UX-only with the backend as the sole enforcement point regardless of what the client last rendered — this is that same principle applied to a cap that happens to be time-varying; `kart-admin-service`'s own grant table already checks live, per request (`kart-admin-service/edge-cases.md`'s stale-permission edge case), so no new server logic is needed, only reuse of existing client messaging.
  - Trade-off accepted: A Support Agent can experience a surprise "this got escalated to Admin" outcome for a request that looked approvable moments earlier, rather than an ideally pre-emptive greyed-out state — accepted because live-syncing every viewer's grant would add real-time infrastructure this app doesn't otherwise need (`architecture.md` marks WS/SSE optional, not required, at launch).
- **Status:** Resolved.

## Edge Case: Multi-Tab BroadcastChannel Doesn't Propagate a Mid-Session Grant/Role Change

- **What happens:** A user has the console open in multiple tabs (e.g., one tab on `support-console`, another on an `Admin`-only screen if their grants span both, or simply two tabs of the same feature); an Admin edits that user's category grant or refund cap mid-session. The `BroadcastChannel('kart-admin-session')` sync only propagates session/idle-timer/logout state (`security.md` §2.2) — nothing about it covers a grant change — so the other open tabs keep rendering controls gated on the grant fetched at their own last page-load until that tab happens to navigate or reload.
- **Why it happens:** `security.md` §2.2 defines the channel's payload narrowly ("any tab's interaction resets the shared idle timer... a warning popup or logout in any tab is mirrored") — a permission-grant change is a materially different kind of event than session lifecycle, and neither that spec nor `requirement-spec.md` §5 extends the channel to cover it.
- **Solutions available (3):** Extend the same channel (or a sibling one) to also carry a lightweight "your grants changed, re-fetch" signal, pushed whenever an Admin edits any principal's grant · Leave it session-only, relying on the fact that every write is server-enforced regardless of stale client-rendered UI (`requirement-spec.md` §5) — a stale enabled control simply gets rejected server-side if the grant was actually revoked, same pattern as the cap-change edge case above · Force a full re-authentication/token refresh on every navigation, defeating silent-refresh convenience
- **Decision:**
  - Chosen: Leave the `BroadcastChannel` scoped to session lifecycle only — no grant-change propagation channel added.
  - Why: `requirement-spec.md` §5's "UX convenience, not the enforcement point" rule already guarantees no actual privilege escalation results from a stale-rendered control (`kart-admin-service/edge-cases.md` confirms its fine-grained check is consulted live, per request, server-side); building a second real-time propagation channel purely for multi-tab UI freshness is speculative infrastructure for a spec that explicitly says to "expand on demand rather than front-loading" (`requirement-spec.md` §1).
  - Trade-off accepted: A user can see an enabled-looking control in a stale tab until that tab's own next navigation/reload after their grant changes, and will hit a late server-side rejection rather than an immediately-updated disabled state — cosmetic staleness, not a security gap.
- **Status:** Resolved.

## Edge Case: Direct-URL Navigation to a Category-Gated Route the Session's Grant Doesn't Cover

- **What happens:** A user manually types, bookmarks, or is sent a direct URL into a gated route their session's grant doesn't cover (e.g., a Support Agent hitting an `identity-admin` URL, or an Admin holding only `catalog-management` hitting a `user-suspension` screen) — bypassing whatever conditional menu/link rendering would normally have kept that route out of view.
- **Why it happens:** `architecture.md`'s route table states guards "reflect role... UX only, not enforcement" — a route guard is a client-side check the browser executes on navigation, and a hand-typed/bookmarked/shared URL reaches the Angular router directly without passing through the menu-rendering logic that hides the entry point; neither `requirement-spec.md` nor `architecture.md` specifies what the guard actually *does* on failure.
- **Solutions available (3):** Route guard redirects to a dedicated "Access Denied" component with a clear explanation · No dedicated guard behavior — render the route normally and let every API call inside it fail with 403, surfaced via each component's own error-toast/empty-state handling · Redirect silently to the dashboard with no explanation
- **Decision:**
  - Chosen: Dedicated Access Denied route/component, reusing `@kart/design-system`'s shared empty-state illustration wrapper (`design-system.md`'s Shared Components row) rather than a one-off implementation per feature.
  - Why: Consistent with this app's WCAG 2.2 AA bar (`requirement-spec.md` §4) — a silent redirect or a shell full of individually-failing API calls is confusing and inconsistent across features, whereas one shared guard behavior is cheap to build once against an already-existing shared component and gives a clear, honest answer every time.
  - Trade-off accepted: Every feature's route guard must consistently invoke the same shared Access-Denied path rather than improvising per feature — a review/lint discipline item, not a framework-enforced guarantee, since Angular guards are configured per-route.
- **Status:** Resolved.

## Edge Case: Privacy Requests View's Blanket "Any Admin" Read Access Over-Exposes GDPR-Sensitive Data

- **What happens:** `privacy.md` §B.9 extends the existing Audit & Compliance dashboard with a new "Privacy Requests" view — but `requirement-spec.md` §3.5 defines that dashboard's underlying audit viewer as "deliberately readable by any `Admin`-role holder regardless of category grant." Applied unmodified, every Admin — regardless of which of the four operational categories (catalog, coupon, suspension, inventory-replenishment) they actually hold a grant for — can see every user's GDPR rights-request (who requested erasure/export, and why), not just Admins with a relevant compliance grant.
- **Why it happens:** §3.5's blanket-readability rule was designed for `AdminActionPerformed` audit events, where "any Admin can audit any admin action" is the entire point of an audit trail. `privacy.md` §B.9 reuses that same screen "rather than building a parallel one" for a materially different data class — customer PII/rights-requests, not admin-action metadata — without re-deriving whether the blanket-read premise still holds for GDPR-sensitive data, where data-minimization is itself a compliance obligation, not just a nice-to-have.
- **Solutions available (3):** Reuse §3.5's existing blanket-any-`Admin` read access unmodified for the Privacy Requests view too, treating it as the same trust tier as action-audit data · Gate the Privacy Requests view behind the `permission-management` category grant (or a new dedicated compliance category), narrowing it below the dashboard's general blanket rule · Show the view to any Admin but redact/mask the requesting user's PII unless the viewing Admin holds a specific grant, exposing only aggregate counts/status otherwise
- **Decision:**
  - Chosen: gate the Privacy Requests view behind a new dedicated `compliance` category grant (option 2) — **not** the dashboard's blanket any-`Admin` rule.
  - Why: GDPR's data-minimization principle (Article 5(1)(c)) is a legal baseline, not a style preference — it applies to who may *view* rights-request data inside the organization just as much as to how long the platform retains it. Blanket reuse was chosen in `privacy.md` §B.9 for engineering-simplicity reasons only, without re-examining the access-control question for this materially different, more sensitive data class; the conservative, compliance-safe default is the correct one to ship, not a placeholder pending further sign-off. This reuses `kart-admin-service`'s existing category-grant mechanism (`requirement-spec.md` §6's "permission-management" pattern) — adding one new category value, not a new access-control mechanism.
  - Trade-off accepted: an `Admin` without the `compliance` grant sees the general Audit & Compliance dashboard (§3.5) but not the Privacy Requests sub-view, a narrower default than that dashboard's other content — an explicit, intentional exception to the "any Admin reads any audit data" rule, scoped to PII-sensitive rights-requests only, stated here so it isn't mistaken for an oversight later.
- **Status:** Resolved, final. Adding the `compliance` category value to `kart-admin-service`'s existing grant enum is captured as a ticket (`tickets.md`) — no new mechanism, no blocking policy dependency.

## Edge Case: Chat UI Receives a Backend Response Shape It Doesn't Recognize (Contract Drift Across Independently-Deployed Services)

- **What happens:** `POST /v1/ai-assistant/query` returns a 200 whose body doesn't match any of the four shapes the Chat UI knows how to render — a normal answer (`answer`/`data`/`visualization`/`metadata`), a clarification (`clarification.question`/`options`), an unsupported-capability response, or one of the named error `type`s (`genai-business-assistant-spec.md` §19/§21.1) — e.g. a future `kart-ai-assistant-service` release adds a new response variant the deployed frontend build predates.
- **Why it happens:** `kart-ai-assistant-service` is an independently-deployed bounded context (ADR-0024) reached only via `kart-api-gateway` (`architecture.md`'s new dependency row) — its release cadence is decoupled from `kart-admin-web`'s own, so the two sides of a REST contract are never guaranteed to be on the same version at the same moment. `requirement-spec.md` §3.6 and the source spec's own client responsibility statement (§11: "renders the conversation, table, and chart; holds no business logic") describe the four known shapes but say nothing about a fifth, unrecognized one.
- **Solutions available (3):** No explicit handling — an unrecognized shape falls through to whatever the rendering code does by default (undefined/blank behavior, effectively a silent failure) · Throw and let the surrounding error boundary blank the whole chat panel · Explicit fallback: any response body that doesn't match one of the four known discriminants is treated as a distinct "couldn't process this response" client-side error state — a friendly message plus a Retry action — with the raw (unrecognized) shape logged client-side for observability, never partially rendered
- **Decision:**
  - Chosen: Explicit unrecognized-shape fallback, treated as its own state distinct from the four backend-defined response types, with client-side logging of the offending shape.
  - Why: `genai-business-assistant-spec.md` §11 scopes this app to "holds no business logic," but recognizing which of a small closed set of response discriminants applies is presentation logic, not business logic — silently doing nothing or blanking the whole panel both fail this app's WCAG 2.2 AA bar (`requirement-spec.md` §4) by leaving the user with no actionable state; this mirrors the platform's general preference for failing closed and explicitly rather than silently, and gives engineers a signal (the logged shape) when a version-skew gap opens between the two services.
  - Trade-off accepted: One more UI state and its own test coverage for a case that, given disciplined API versioning between the two independently-deployed services, should be rare in practice — it contains the blast radius of a contract change, it does not substitute for the two teams actually coordinating breaking response-shape changes.
- **Status:** Pending human review (new, added for §3.6 AI Assistant).

## Edge Case: A Second AI Assistant Question Submitted, or the Feature Navigated Away From, While a Prior Query Is Still In Flight

- **What happens:** The user submits a question, and before the response lands (latency is an explicit, still-open SLA question — `genai-business-assistant-spec.md` §18 "recommend a working target of a few seconds... pending a human-set SLA") either types and submits a second question, or navigates to a different `kart-admin-web` feature area (or closes the tab).
- **Why it happens:** `requirement-spec.md` §3.6 describes "a single free-text conversational interface — one chat panel per conversation session," but neither it nor `design-decisions.md`'s Signal Store decision states what the client does with its one input while a turn is outstanding; the backend's own "Concurrent Requests in the Same Conversation Session" edge case (`kart-ai-assistant-service/edge-cases.md`) only decides what the *backend* does once two overlapping requests arrive on the same `conversationId` (serialize, reject the second with "still processing") — it does not stop the client from creating that condition in the first place, nor does it say what should happen to a request whose result will render into a component the user has already navigated away from.
- **Solutions available (3):** Let the user submit freely — a second submit fires a second concurrent HTTP call, relying entirely on the backend's own per-`conversationId` serialization to reject the second one with its "still processing" message · Disable the chat input/submit control for the duration of the outstanding request (only one turn can ever be in flight from this tab), using the loading/in-flight status field `design-decisions.md`'s Signal Store already holds · Both disable the input while in flight, and abort the outstanding HTTP request (`AbortController`) if the user navigates away from the `ai-assistant` feature route before it resolves
- **Decision:**
  - Chosen: Disable the chat input while a request is in flight (surfacing the existing loading state as a visible typing/"thinking" indicator), and abort the in-flight request if the user navigates off the `ai-assistant` route before it resolves.
  - Why: Disabling input matches the "one chat panel, one conversation" shape §3.6 already describes — a user is never meant to have two turns of the same conversation outstanding at once, so this is the primary UX mechanism, not a reliance on the backend's serialization rejection as the user-facing behavior (that rejection remains a safety net for the residual double-submit/retry case, same posture as the backend's own edge case). Aborting on navigation is ordinary Angular component-lifecycle cleanup (unsubscribing/cancelling on `ngOnDestroy`) and prevents a late response writing into a feature-scoped Signal Store no component is reading, consistent with `design-decisions.md`'s framing of that store as a thin, disposable UI-state mirror, not a source of truth.
  - Trade-off accepted: A client-side abort does not guarantee the backend request itself stops executing or the LLM call it triggered is cancelled — that is a backend/cost-control concern (§18's own open "Cost" NFR question), not something this app's abort can or should reach into; disabling input for the full latency window also means an impatient user cannot revise a bad question mid-flight without waiting for it to resolve or navigating away first, an accepted UX cost given the alternative (letting concurrent turns race) is strictly worse per the backend's own edge case reasoning.
- **Status:** Pending human review (new, added for §3.6 AI Assistant).

## Edge Case: Frontend Receives a `visualization.type` Enum Value It Has No Renderer For

- **What happens:** A response's `visualization.type` is a value the Chat UI's ECharts-based rendering layer (`design-decisions.md`'s "Chart Rendering" decision) doesn't have an explicit case for — either a genuinely new value added to the backend's enum in a later release the frontend hasn't caught up to yet, or (less likely, since `ngx-echarts` was chosen specifically to cover the full day-one enum) a gap in what's actually been wired up for one of the seven current values (`bar_chart, horizontal_bar_chart, line_chart, donut_chart, funnel_chart, single_stat, table_only`).
- **Why it happens:** `kart-ai-assistant-service` and `kart-admin-web` are independently deployed (ADR-0024, `architecture.md`), so the enum on the wire and the set of renderers actually shipped in the currently-deployed frontend build are never guaranteed to be in lockstep — the same version-skew root cause as the unrecognized-response-shape edge case above, but scoped specifically to `visualization.type` rather than the whole response shape. `genai-business-assistant-spec.md` §19 already defines a backend-side fallback for a *different* trigger — "chart type can't render the *returned shape*" (a data-shape mismatch on a recognized type) falls back to `table_only` — but says nothing about the frontend being asked to draw a type value it was never given a renderer for at all.
- **Solutions available (3):** Render nothing / leave a blank chart area for an unmatched `visualization.type` · Throw, failing the whole response's render — which would violate FR-005/§13.2's own guarantee that "a table is never omitted in favor of a chart alone," since a thrown render error could take the already-fetched table down with it · Client-side default-case fallback: any `visualization.type` not matched by an explicit renderer case renders as `table_only` (the data table renders regardless, per FR-005), mirroring the backend's own visualization-failure fallback semantics at the render layer instead of only at the backend's assembly layer
- **Decision:**
  - Chosen: Client-side default-case fallback to `table_only` for any unrecognized/unimplemented `visualization.type`, with the unmatched type value logged client-side for observability.
  - Why: FR-005/§19 already establish `table_only` as this capability's answer to "a chart can't be produced for this turn" — reusing that exact, already-familiar fallback for a frontend-side rendering gap keeps one consistent user-facing behavior regardless of which layer (backend assembly vs. frontend rendering) is the one that couldn't produce a chart, rather than inventing a second, differently-shaped degraded state; it also directly protects against the two services' independent deploy cadence ever producing a version-skew gap that would otherwise blank or break the panel.
  - Trade-off accepted: This can mask a real frontend gap (a genuinely new enum value nobody has built a renderer for yet) behind a graceful-looking `table_only` result rather than surfacing it as a visible defect — mitigated only by the client-side log of the unmatched type, which must actually be watched in monitoring for this to be caught before a user notices the "missing" chart on their own.
- **Status:** Pending human review (new, added for §3.6 AI Assistant).

## Edge Case: `conversationId` Continuity Across Browser Refresh, Tab Close, and Multiple Open Tabs

- **What happens:** A user mid-conversation refreshes the tab, closes and reopens it, or opens the AI Assistant feature in a second tab of the same login session — it is undecided whether the chat panel resumes the same conversation (same `conversationId`) or always starts a fresh one, and, if a `conversationId` were shared across tabs, whether two tabs could end up racing on the same backend session.
- **Why it happens:** `requirement-spec.md` §3.6 states "one chat panel per conversation session" but doesn't scope what a "session" is bounded by (browser tab vs. login session vs. persisted-across-restarts). `design-decisions.md`'s Signal Store decision frames the client store as "a thin mirror" holding only "the rendered message list, in-flight/loading/error status, the current draft input" — an in-memory Angular Signal Store is, by construction, wiped on refresh since it lives in JS heap, not persisted storage — so today's behavior (always-fresh-on-refresh) is only an accident of where the state happens to live, not a stated decision. Separately, `security.md` §1 forbids ever writing a *token* to `localStorage`/`sessionStorage`, which constrains but doesn't by itself answer where a non-token identifier like `conversationId` may safely persist; and the backend's own "Concurrent Requests in the Same Conversation Session" edge case (`kart-ai-assistant-service/edge-cases.md`) would reject a second tab's turn if two tabs ever shared one `conversationId` and both sent messages close together.
- **Solutions available (3):** Persist `conversationId` only (never message content/history) in `sessionStorage`, which is natively tab-scoped in every evergreen browser — a refresh resumes the same conversation, but each new tab always gets a new one · Persist `conversationId` in `localStorage`, shared across every tab of the same origin, so all tabs of one login session share one conversation · No persistence at all — every refresh and every new tab always starts a brand-new `conversationId`, discarding in-progress conversational context (§14) on any accidental reload
- **Decision:**
  - Chosen: Persist only `conversationId` (never the rendered transcript) in `sessionStorage`, tab-scoped. A refresh resumes the same conversation by reusing the stored `conversationId` on the next request; the visible message transcript itself is not restored/replayed client-side, since the authoritative "last resolved structured intent" a follow-up merges against already lives server-side (`genai-business-assistant-spec.md` §14.1) and the client store never persisted transcript content by design. No `localStorage` sharing across tabs.
  - Why: `sessionStorage`'s native tab-isolation answers both the refresh question and the multi-tab question with one mechanism, consistent with this app's existing precedent of choosing a storage API for its exact isolation semantics rather than defaulting to the broadest one (`security.md` §1's `HttpOnly` cookie for the token; `security.md` §2.2's `BroadcastChannel` scoped deliberately to one browser profile, not cross-device) — and it structurally prevents the two-tabs-same-`conversationId` race the backend's own "Concurrent Requests" edge case would otherwise have to reject with a visible "still processing" error, since every tab now deterministically gets its own conversation. Resuming (rather than discarding) the `conversationId` on refresh honors G3/§14's emphasis on natural conversational follow-up — a follow-up-heavy workflow shouldn't lose all context to an accidental reload when the backend has nothing to lose by staying attached to the same session.
  - Trade-off accepted: A refreshed panel shows an empty transcript while still behaving as an in-context follow-up on the next message — a state that can look surprising (no visible history, yet a contextually-aware answer) unless the UI states this plainly (e.g., a one-line "conversation resumed" notice) rather than implying the panel's visible state is more complete than it is; a user who deliberately wants two independent, parallel conversations must open two tabs (treated as an acceptable, even expected, way to get that outcome, not a gap).
- **Status:** Pending human review (new, added for §3.6 AI Assistant).

## Edge Case: AI Assistant's Long-Running Read-Only Query Not Recognized as "Activity" by the Existing Idle-Timer Pause Rule

- **What happens:** A user submits an AI Assistant question and is waiting on a response whose latency is explicitly an open SLA question (`genai-business-assistant-spec.md` §18: "a few seconds" as a working target only, pending a human-set figure, with the backend's own bounded-retry-then-fallback chain able to stretch a slow turn further still); during that wait, the existing 60-second idle-timeout warning modal can fire, or the idle timer itself can lapse, even though the user is actively engaged with the console — because the existing idle-session state machine (`design-decisions.md`'s "Idle-Session Client State Machine") only pauses its countdown for an *outstanding mutating request*, and an AI Assistant query is explicitly read-only (`requirement-spec.md` §3.6: "the assistant never mutates any business data"; NG8), so it doesn't qualify under that rule as currently scoped.
- **Why it happens:** The pause-on-in-flight-write rule was designed and justified specifically for the money-moving refund-approval race (this file's own "Idle-Timeout Warning Countdown Racing an In-Flight Refund-Approval Submit" edge case, resolved before §3.6 existed) — its "an agent mid-submit is by definition actively working, not idle" reasoning applies just as well to a user mid-question in the chat panel, but §3.6 is a new feature added after that decision was made, and nothing has revisited the rule's scope to include it.
- **Solutions available (3):** Leave the pause rule scoped to mutating requests only, accepting that a slow AI Assistant answer can be interrupted by an idle warning or idle logout mid-wait · Extend the existing in-flight-request counter that feeds the idle-timer pause to also treat any outstanding call to `kart-ai-assistant-service` as activity, regardless of it being read-only, pausing the countdown the same way a mutating write already does · Rely solely on the fact that submitting the question itself already reset the idle timer (true today, via ordinary user interaction), accepting a long enough wait as a legitimate idle-timeout trigger like any other period of no further interaction
- **Decision:**
  - Chosen: Extend the in-flight-request counter to also treat an outstanding AI Assistant query as activity, pausing the idle countdown identically to a mutating write, resuming normal idle-counting only once the response (success, clarification, or error) lands.
  - Why: The state machine already exists as shared infrastructure precisely so "the idle timer, the refresh interceptor, and the HTTP layer... share one coordinated state" (`design-decisions.md`) — extending its counter to one more request class is a small scope change to already-built infrastructure, not new infrastructure; the original edge case's own reasoning ("actively working, not idle... timing out under them is a false-positive idle detection, not a security win") was never actually specific to the request being a *write* — it turns on the user actively waiting on a response, which is equally true for a read.
  - Trade-off accepted: This extends, rather than closes, the residual gap the original idle-timeout edge case already flagged — "a stuck/hung request can hold the idle timer open indefinitely unless paired with a client-side request-timeout ceiling (not fixed by this pass)" — to a second request class (an abandoned or hung AI Assistant query now also keeps the idle timer paused for as long as it stays outstanding); this pass does not add that timeout ceiling either, it only applies the already-accepted trade-off consistently across both request classes rather than leaving AI Assistant queries as an unintentional exception.
