# DDD Model: kart-shopping-assistant-service

**Pipeline-order note.** This is the first `ddd-model.md` pass for this service, exactly as it was for `kart-ai-assistant-service` — there is no pre-existing schema to reconcile against; the Database Design Agent runs after this document, not before it.

**Input-freshness note.** `requirement-spec.md`, `edge-cases.md`, `design-decisions.md`, and `architecture.md` are all `status: approved`, each with its own `approval_note` stating that the remaining open items (Architecture-1/2, Data-1/2/3, Security-1, Business-1/2/3, UX-1/2, NFR-2/3) are non-blocking for Architecture/DDD/API/Database work. This document invents no numeric value for any of them (session TTL, pending-confirmation TTL, idempotency-key replay window, circuit-breaker/latency/cost figures) and models every aggregate to be agnostic of the exact numbers.

## Boundary Summary

`kart-shopping-assistant-service` is, in DDD terms, an **orchestration/control-plane caller** across nine existing bounded contexts (architecture.md's Boundary Rationale) — the same relationship `kart-ai-assistant-service` holds toward `kart-analytics-service` (ADR-0024), generalized here to nine peers and to mutating, not merely read-only, calls. **ADR-0028 closes this service's data-ownership boundary at exactly three owned structures** — conversation/session state, its own audit log, and (per design-decisions.md's own explicit hand-off, resolved in this document) an idempotency-ledger structure — and forecloses anything Order/Cart/Payment/Offer/Product/User/Delivery-Tracking-shaped. This is the ceiling this document works to, not a floor: **exactly three aggregate roots**, below.

## Note on an Inherited Documentation Inconsistency (Resolved Here, Not Silently Picked)

`design-decisions.md`'s **Confirmation-Before-Mutation State Machine** decision is explicit and reasoned: `pending_confirmation` *and* the broader "last-resolved intent/slots" conversational context both live in the platform's shared **Redis** deployment, "mirroring `kart-ai-assistant-service/design-decisions.md`'s own Conversation-Session-Storage precedent (same Redis deployment, same 'ephemeral, TTL-bound, per-key, no cross-key relational structure' profile)." `architecture.md`'s Component/Boundary Diagram and Dependencies table agree with this (the Redis node explicitly lists "pending-confirmation · last-resolved-intent/slots"). However, `architecture.md`'s own **Deployment/Scaling Posture** section separately states: *"Durable state — `ConversationSession`, `AuditRecord`, and `idempotency_keys` — lives in this service's own PostgreSQL database"* — placing the same conceptual session state in Postgres, contradicting its own diagram and directly re-opening a storage-technology decision `design-decisions.md` already fixed with dedicated reasoning (which `architecture.md`'s own frontmatter/Boundary Rationale states it works "within ADR-0028/0029/0030's already-fixed guarantees," not a license to re-decide a design-decisions.md-level call).

**Resolution adopted by this document:** the session-state aggregate below is modeled as **Redis-backed, ephemeral, TTL-bound**, per `design-decisions.md`'s dedicated, reasoned decision — the more specific and more authoritative source on this exact data-placement question. `architecture.md`'s Deployment/Scaling Posture paragraph's inclusion of "`ConversationSession`" in its Postgres-durable-state list is treated as an inherited drafting inconsistency to flag forward for correction at that document's next revision, not as a re-decision this pipeline stage is bound to follow. This is reported back to the orchestrating run as a finding, not silently absorbed.

## Aggregate: `ShoppingAssistantSession`

**Entity:** `ShoppingAssistantSession` — identified by `ShoppingAssistantSessionId` (an opaque identifier this service generates on a conversation's first turn and the client supplies on every subsequent turn, the same lifecycle `kart-ai-assistant-service`'s own `ConversationId` already established for its analogous concept). Backed by Redis, per-session key namespace (`shopping-assistant:session:{sessionId}`, design-decisions.md's Confirmation-State-Machine decision) — see the inconsistency note above for why this is Redis, not Postgres.

**Value objects:**
- `ResolvedShoppingIntent` — `{ intentName, resolvedSlots }`, the last resolved intent + its slots (requirement-spec §5's "resolved-but-unconfirmed mutating intent" language; FR-007). `intentName` is a plain string validated, at resolution time, against the external Intent Catalog registry (see below) — the validation is an application-layer precondition, not an invariant this value object enforces on itself. `resolvedSlots` is a map from slot name to either a plain scalar (`quantity: int`, `reasonCode: string`) or an `ExternalResourceReference` (see below) for any slot that names a foreign resource (`orderId`, `cartId`, `addressId`, `sku`, `couponCode`).
- `PendingConfirmation` — `{ intentName, resolvedSlotsSnapshot, createdAt }`, the FR-004 confirmation-awaiting-a-yes/no state (design-decisions.md's Confirmation-Before-Mutation State Machine decision). Exists **only** for a mutating intent — a read-only intent never populates this field (FR-004 is scoped to mutating actions only).
- `ExternalResourceReference` — see its own reasoning section below; used inside `resolvedSlots` and, by value, on `ShoppingAssistantAuditRecord`.

**Fields:** `sessionId: ShoppingAssistantSessionId`, `principalId` (nullable — the authenticated `Customer`'s opaque `UserId`, absent for a guest caller), `lastResolvedIntent: ResolvedShoppingIntent` (nullable, absent before the session's first resolved turn), `pendingConfirmation: PendingConfirmation` (nullable), `lastActivityAt` (the sliding-idle-TTL anchor, same pattern as the sibling service).

**Invariants:**
- **Exactly one mutable "current" resolved intent per session, never a history.** A follow-up turn overwrites `lastResolvedIntent` wholesale (fields the new message didn't address are carried forward into the new value, FR-007); the full sequence of intents a conversation passed through is reconstructable only from the append-only `ShoppingAssistantAuditRecord` trail, never from this aggregate.
- **`pendingConfirmation` is explicitly cleared, not left to passive TTL expiry, the instant FR-002 (re-)resolves any new intent in a later turn — mutating or not.** This is the DDD-terms restatement of edge-cases.md's "Follow-up Message That Should Reset vs. Carry Forward a Pending Mutating Confirmation" decision and FR-007's "never silently carried forward across a topic switch." See "Consistency Boundary" below for why this must be one atomic write against this one aggregate.
- **A newly (re-)resolved mutating intent always requires a fresh FR-004 confirmation cycle.** A prior `pendingConfirmation` value is never reused to authorize execution of a later-resolved intent, even if `intentName` happens to match — the discard-on-topic-switch decision is unconditional (edge-cases.md: "any newly (re-)resolved intent, ambiguous or not, requires a fresh FR-004 confirmation").
- **Per-session serialization: at most one turn is processed at a time per `ShoppingAssistantSessionId`.** Unlike the read-only sibling (for which this is a UX/data-consistency nicety), this is **load-bearing for the idempotency invariant itself** — it only guarantees "one key per attempted action" if exactly one turn is ever allowed to attempt a given mutating action at a time (edge-cases.md "Concurrent/Duplicate Mutating Turns in the Same Conversation Session," design-decisions.md's chosen per-session lock/queue mechanism).
- **`principalId` may transition exactly once, from absent (guest) to a specific authenticated `Customer`'s `UserId` — never reassigned from one non-null principal to a different one within the same aggregate instance.** This formalizes edge-cases.md's "Guest Session Attempts a Mutating Intent Mid-Conversation After Starting Read-Only" (the legal guest→authenticated upgrade, preserving already-served read-only context) while closing an unaddressed gap: nothing in the upstream documents states what happens if a *different* authenticated identity tried to reuse an existing session's accumulated context, so this document fixes it as a fresh engineering default, flagged as such — a genuinely different authenticated caller always begins a new `ShoppingAssistantSession`, never rebinds an existing one.
- **`principalId` is never treated as an authorization credential by this service itself.** It exists only to gate which turns may currently be attempted (FR-001) and to attribute already-served read-only context across a guest→authenticated transition — **every downstream mutating call forwards the caller's live, currently-presented JWT, never a value read from this aggregate.** This is the DDD-model formalization, in this document's own words, of requirement-spec §5's no-cross-customer-action invariant and edge-cases.md's "A Resolved `orderId`/`cartId`/`addressId` That Stops Belonging to the Caller Mid-Session" resolution: a resource id sitting in `resolvedSlots` is never locally re-validated for ownership by this service — it is forwarded downstream, opaque, so that the owning service's own per-resource check is what actually gates the mutation, every single time, regardless of what this aggregate happens to hold.
- **TTL-agnostic of the exact idle duration.** The concrete session/pending-confirmation TTL figures are UX-2 (requirement-spec §10) — genuinely open, not invented here; the structural rule fixed by this model is that once expired, no follow-up may be resolved against an absent session, and an orphaned follow-up must surface a distinguishable "expired" response, never be silently misread as if `lastResolvedIntent` were still present.
- **Never holds a durable copy of another bounded context's owned data.** `resolvedSlots`' `ExternalResourceReference` values are opaque ids only; any richer display detail this service fetches to compose one turn's confirmation/summary text (an order's line items, a full address string, a masked payment label) is ephemeral, request-scoped application state — never a field on this aggregate. Only a bounded natural-language echo of it, if anything, survives past the turn — on `ShoppingAssistantAuditRecord`'s own `responseSummary`, described below, never here.

### Modeling Decision: `pendingConfirmation` Is Inside `ShoppingAssistantSession`'s Own Consistency Boundary — Not a Separate, Redis-Native Concern

The task this document must settle explicitly: does `pending_confirmation` belong inside this aggregate's transaction boundary, or is it a separate concept this aggregate merely references?

- **Physical co-location is a signal, not the deciding test.** Both `design-decisions.md` and `architecture.md` describe `pending_confirmation` and the broader last-resolved-intent/slots context as living in the *same* Redis deployment, under the *same* per-session key namespace — already suggestive of one record, but not on its own sufficient (two logically separate keys sharing a namespace prefix would still be two things).
- **The deciding test is the transaction-boundary test (`ddd-agent.md`; `ddd-cqrs-standards.md`), applied to the one invariant that actually needs it.** Edge-cases.md's own resolved decision requires `pendingConfirmation` to be cleared **atomically with** any new intent resolution — "explicitly cleared to null the instant FR-002 resolves any new intent in a later turn... not left to passive TTL expiry alone" (design-decisions.md, quoting its own reasoning). If `pendingConfirmation` were a second, independently-written Redis structure, a crash or partial failure between "write the new `lastResolvedIntent`" and "clear `pendingConfirmation`" could leave a stale confirmation alive alongside a freshly-resolved, *different* intent — precisely the "silently carried forward across a topic switch" outcome FR-007 forbids. Only one aggregate, written through one code path against one consistency boundary, makes "clear atomically with any new resolution" an enforceable invariant rather than a best-effort two-step sequence that can partially fail.
- **The differing TTL (design-decisions.md: `pending_confirmation`'s "own short TTL, independent of and shorter than the broader conversation-context TTL") is an expiry-*policy* detail, not evidence of a second aggregate.** Many single aggregates hold fields with independently-expiring lifetimes — `kart-order-service`'s own `IdempotencyKey` lives directly on the `Order` aggregate (glossary: "no separate ledger... since no external call sits between reserving it and committing the order") despite representing a narrower-lived fact than the order itself. TTL asymmetry is a schema/database-design-level concern (e.g., a shorter native Redis key-level expiry on just the confirmation half, or a Lua-scripted/`MULTI`/`EXEC` joint write), not a reason to split the domain model.
- **Conclusion:** `pendingConfirmation` is modeled as a field within `ShoppingAssistantSession`'s own aggregate/consistency boundary. The Database Design Agent may still implement it as a physically distinct Redis key for TTL-granularity reasons, provided whatever mechanism it chooses preserves the atomic-clear-on-new-resolution guarantee this invariant requires — that is an implementation-mechanism question, not a domain-boundary one.

## Aggregate: `ShoppingAssistantAuditRecord`

**Entity:** `ShoppingAssistantAuditRecord` — identified by `ShoppingAssistantTurnId` (generated once per processed turn). Backed by this service's own durable Postgres store (design-decisions.md's `kart_shared.auditing`/RLS decisions apply to this table) — must remain queryable after the `ShoppingAssistantSession` describing the same conversation has expired, mirroring the sibling's own reasoning.

**Modeled as its own aggregate root, not a child of `ShoppingAssistantSession` — confirmed by the same three-part test the sibling document already used:**
1. **Different transaction boundary** — Redis vs. Postgres; they can never share one ACID transaction.
2. **Different lifecycle** — a turn's audit record must outlive the session's TTL (requirement-spec §6's audit requirement).
3. **Different query pattern** — queried by `turnId`, by `sessionId` (transcript reconstruction), or by `principalId`/date range for compliance — none of these are natural sub-queries of "one session's current state."

**Value objects — deliberately a richer set than the sibling's, per requirement-spec §6's own explicit reasoning ("the log is not metadata-only by default here"):**
- `ResolvedShoppingIntent` — the same value-object shape defined above, embedded here as an immutable, frozen copy of whatever intent this specific turn resolved (or absent, for a turn that never reached a resolved intent).
- `ProposedActionRecord` — `{ intentName, targetResource: ExternalResourceReference, actionDescription }`, present only when this turn's resolved intent is mutating: **what mutating action was proposed**, and **against which resource** — the field-level answer to requirement-spec §6's own reasoning for why this audit record must be richer than the read-only sibling's.
- `ConfirmationOutcome` — `{ confirmedAt, affirmed: bool }` (nullable), present iff FR-004's confirmation step was actually reached this turn: **what was confirmed** (or declined). The exact UX affirmation mechanism (button vs. typed "yes") is UX-1, genuinely open — this value object records only the fact and timing of confirmation, not the mechanism.
- `ExecutionOutcome` — `{ executedAt, downstreamEndpoint, downstreamOutcome, downstreamStatusCode, idempotencyKeyRef }` (nullable), present only if the mutating call actually fired: **what was executed**, against which downstream endpoint, with what outcome (`Success | Rejected | PartialFailure`, FR-005's "a `409` is explained truthfully, never silently retried"), and a reference to the `ShoppingAssistantIdempotencyKey` used (see Cross-Aggregate Interaction below).
- `ClarificationDetail` — `{ question, options }`, present iff `turnOutcome = ClarificationIssued` (FR-008).
- `ErrorDetail[]` — `{ category, message }`, zero or more per turn; `category` is one of `unsupported-gap` (rows 8/10, FR-010), `ambiguous`, `unauthenticated-mutating-rejected` (FR-001), `downstream-rejected` (FR-005's authoritative `409`), `partial-failure` (FR-009), `injection-detected-non-actionable` (edge-cases.md's prompt-injection case, when the containment/firewall actually intervened), `expired-session`, `timeout-or-circuit-open` (design-decisions.md's per-edge breaker decision).
- `ResponseSummary` — `{ summaryText }` (bounded length, never the full raw fetched payload) — the natural-language text actually sent this turn, mirroring the sibling's `FinalResponseSummary` discipline, but extended here to also cover FR-004 confirmation text, not only FR-006 summaries, per edge-cases.md's "Confirmation or Summary Text Implies a Capability That Doesn't Exist" decision (the grounding check applies to both).
- `GroundingCheckResult` — `Pass | Fail`, recording the outcome of that (possibly twice-applied, per the item above) grounding check for this turn.

**Fields:** `turnId: ShoppingAssistantTurnId`, `shoppingAssistantSessionId` (opaque reference, never a foreign key — see invariant below), `principalId` (nullable), `turnOutcome: (Successful | ClarificationIssued | ConfirmationPending | Error)`, `resolvedIntent: ResolvedShoppingIntent` (nullable), `proposedAction: ProposedActionRecord` (nullable), `confirmationOutcome: ConfirmationOutcome` (nullable), `executionOutcome: ExecutionOutcome` (nullable), `clarificationDetail: ClarificationDetail` (nullable), `errors: ErrorDetail[]`, `responseSummary: ResponseSummary`, `groundingCheckResult: GroundingCheckResult`, `correlationId` (architecture.md's Observability requirement: end-to-end trace propagation), `timestamp`.

**Invariants:**
- **Exactly one `ShoppingAssistantAuditRecord` per turn, always — successful, clarification, confirmation-pending, or error alike.** Requirement-spec §6's own acceptance criterion, restated as this aggregate's creation rule.
- **Append-only, immutable once written** — no field is ever updated or deleted after creation, the same posture every other append-only audit aggregate on this platform holds.
- **`targetResource` (inside `proposedAction`/`executionOutcome`) is always an `ExternalResourceReference` — an opaque `{ resourceType, resourceId }` pair, never an embedded copy of the referenced order/cart/coupon/address/product record.** The richer PII surface requirement-spec §6 names this service as routinely handling (order contents, full address detail) is captured, if at all, only inside `responseSummary`'s own *bounded* natural-language text — never as a separate structured field that would durably re-own another service's record shape. This is this document's own formalization, in its own words, of ADR-0028's ownership table applied specifically to the audit aggregate.
- **No raw `gateway_token`, or any unmasked PCI-scoped value, is ever a field anywhere on this aggregate.** Only a masked display reference (e.g., "Visa ending 4242") an owning service has *already* returned may ever appear inside `responseSummary`'s bounded text (ADR-0028's ownership table, item 3; requirement-spec §6). This document deliberately does **not** model a dedicated "masked payment reference" value object, since intent row 9's default-payment-method concept is itself a confirmed, unresolved gap (Data-2) — modeling a structured field for data no endpoint yet exposes would be building ahead of a requirement that doesn't exist yet (the same restraint `kart-payment-service/ddd-model.md`'s Modeling Decision #4 already exercises for chargeback-lifecycle depth, and ADR-0026's "no speculative placeholder" discipline, applied here to a different gap).
- **`turnOutcome`, `clarificationDetail`, `errors`, `proposedAction`/`executionOutcome` are independent, non-exclusive facts about one completed turn, not a state machine** — mirrors the sibling's equivalent invariant; the one true structural distinction preserved is FR-010's "unsupported/gap" vs. a genuinely executed mutation, captured via `errors`' `unsupported-gap` category, never conflated with a normal `executionOutcome.downstreamOutcome = Success`.
- **`shoppingAssistantSessionId` is an opaque reference, never a foreign key** — `ShoppingAssistantSession` (Redis) and `ShoppingAssistantAuditRecord` (Postgres) cannot share a referential-integrity constraint across stores, and a dangling reference (an already-expired or never-existent session) is the expected, permanent steady state for every audit row once enough time has passed — identical reasoning to the sibling's `conversationId` invariant.

## Aggregate: `ShoppingAssistantIdempotencyKey`

**Entity:** `ShoppingAssistantIdempotencyKey` — identified by a composite scope value (kept unnamed in the cross-service glossary — see Naming Notes above — described here as `{ shoppingAssistantSessionId, intentName, resolvedSlotsHash }`), directly mirroring design-decisions.md's Idempotency-Key Persistence decision: a dedicated Postgres table with a unique constraint on `(conversation_session_id, intent_name, resolved_slots_hash)`. Reserved *before* the downstream mutating call is fired; the same stored value is returned (never re-minted) on any retry whose scoping tuple matches.

**Modeled as its own aggregate root, separate from both `ShoppingAssistantSession` and `ShoppingAssistantAuditRecord` — resolving design-decisions.md's own explicitly deferred question ("whether it is modeled as its own table or a field set on `AuditRecord` is schema/aggregate design left to the DDD Agent, not decided here"):**
- **Different store from `ShoppingAssistantSession`** (Postgres vs. Redis) — cannot share a transaction by construction, same reasoning as `ShoppingAssistantAuditRecord`'s own split from the session aggregate.
- **Different write timing from `ShoppingAssistantAuditRecord`, even though both live in Postgres.** The key must be reserved (inserted) *before* the downstream mutating HTTP call fires — so a concurrent/retried attempt sees the reservation already present — while the turn's full outcome is only known and recorded on `ShoppingAssistantAuditRecord` *after* that call returns. An external HTTP call cannot participate in a database transaction, so "reserve the key" and "record the outcome" structurally cannot be one transaction — the textbook shape the transaction-boundary test exists to catch, applied here exactly as `kart-payment-service/ddd-model.md`'s Modeling Decision #2 already established for the identical reserve-then-confirm-around-an-external-call problem (`IdempotencyRecord` split from `PaymentIntent`).

**Value objects:**
- The composite scope value described above (`{ shoppingAssistantSessionId, intentName, resolvedSlotsHash }`) — `resolvedSlotsHash` is a deterministic hash of the mutating intent's resolved slots at the moment of the attempt, never the slots themselves in cleartext on this entity (that richer detail is already durably captured, if needed for audit, on the corresponding `ShoppingAssistantAuditRecord.proposedAction`) — this keeps the idempotency table narrowly scoped to its one job (dedup), not a second copy of resolved-slot business data.

**Fields:** the composite scope (above), `mintedKeyValue` (the actual string value forwarded as the `Idempotency-Key` header on the downstream call), `createdAt`.

**Invariants:**
- **Unique per `{ shoppingAssistantSessionId, intentName, resolvedSlotsHash }`** (the DB unique constraint design-decisions.md names) — scoped to a composite tuple, not a bare key, because unlike `kart-order-service`'s single-per-order `IdempotencyKey`, one session can attempt many distinct mutating intents, each needing its own scope.
- **A retry whose scope matches an existing row reuses the stored `mintedKeyValue` verbatim — never mints a second key for the same scope.** This is requirement-spec §5's idempotency invariant, restated as this entity's own creation rule: "generates and persists one idempotency key per attempted mutating action... and reuses it on any internal retry."
- **The replay-window TTL/expiry is not decided here** — design-decisions.md's own "Out of Scope" list names "idempotency-key TTL/replay window" as an open figure; this document does not invent one.

## Referenced, Never Owned: The Intent Catalog (Application Config, Not a Domain Aggregate)

The ~12-row Intent Catalog (requirement-spec §2) — the closed, enumerable registry `ResolvedShoppingIntent.intentName` is validated against — is **not modeled as a domain aggregate or entity anywhere in this document**, for the same three reasons `kart-ai-assistant-service/ddd-model.md`'s Modeling Decision #7 already gives for its own analogous metric/entity/dimension registry, restated in this service's own terms:
1. **It has no per-instance identity or lifecycle to persist.** It is a closed, versioned set fixed at deploy time — design-decisions.md's Bounded Tool-Calling Registry decision realizes it as a decorator-based static Python registry (`INTENT_REGISTRY`), eagerly built once at process import time, never mutated at runtime.
2. **It has no write path from any request handler.** Nothing in this service's own domain logic ever creates, updates, or retires a catalog row — a new intent requires a code change and redeploy (FR-003's own "never LLM-authored" mandate), the same review discipline any other reviewable application config on this platform already follows.
3. **It is referenced by `ResolvedShoppingIntent`/`PendingConfirmation`/`ShoppingAssistantAuditRecord`/`ShoppingAssistantIdempotencyKey`'s `intentName` fields, never redefined or partially modeled by any of them** — each of those fields' own validity is a precondition enforced against the external registry at resolution time, not a rule this document's own value objects enforce on themselves.

Because this registry is authored and lives entirely inside this service's own codebase (not another bounded context's), it is not added to the "Referenced Elsewhere" ACL table below either — it is this service's own application config, explicitly excluded from the domain model, not a cross-context reference.

## Value Object: `ExternalResourceReference` — Reasoning

`ExternalResourceReference` — `{ resourceType: (OrderRef | CartRef | AddressRef | SkuRef | CouponRef), resourceId }` — is the single, generic shape used everywhere this service's aggregates need to name a foreign resource (an `orderId`, `cartId`, `addressId`, `sku`, or `couponCode`), per requirement-spec §5/ADR-0028's ownership table. One generic value object, not five separately-named ones, because the invariant it enforces is identical regardless of which resource type is named:

- **It is opaque by construction — an id and a type tag, nothing else.** This is this document's own formalization, in its own words, of ADR-0028's data-ownership table: this service's aggregates never reference another service's aggregate by anything richer than this pair. There is no field on `ExternalResourceReference` for a cached price, a cached order status, a cached stock level, or any other business fact that resource's owning service would need to compute — that would be exactly the "cache or local recomputation of a number/state a downstream service itself owns" ADR-0028 forecloses (echoing requirement-spec §5's "the assistant never adjudicates eligibility itself").
- **It is never validated for ownership by this service.** Whatever principal resolved this reference into a session's slots, the only thing this service ever does with it downstream is forward it, unchanged, alongside the caller's *live* JWT — the owning service's own per-resource ownership check is what actually gates any subsequent mutation (requirement-spec §5, edge-cases.md's account-switch case). `ExternalResourceReference` itself carries no ownership claim to check.
- **It appears by value in two places — `ShoppingAssistantSession.lastResolvedIntent.resolvedSlots` and `ShoppingAssistantAuditRecord.proposedAction`/`executionOutcome`'s `targetResource` — never by shared reference,** for the identical reason the sibling's `ResolvedIntent` value object is duplicated rather than referenced: the session's copy is live and overwritable turn-to-turn, while the audit record's copy must remain a frozen, indefinitely-queryable snapshot of what was true *at that turn*, even after the session has long since expired or moved on to a different value.

## Domain Invariants (Formalized in This Document's Own Terms, Citing Upstream by Section)

- **A resolved-but-unconfirmed mutating intent is discarded, not carried forward, on a topic switch.** Enforced as `ShoppingAssistantSession`'s own atomic clear-`pendingConfirmation`-on-new-resolution rule (see the dedicated Modeling Decision above) — edge-cases.md's "Follow-up Message That Should Reset vs. Carry Forward a Pending Mutating Confirmation," FR-007.
- **No cross-customer action under any conversational framing.** Formalized as two cooperating rules, neither of which is this service's own judgment call at the point of the mutation: (1) `ShoppingAssistantSession.principalId` is never an authorization credential — it is informational session-scoping state only; (2) every `ExternalResourceReference` this service ever forwards downstream travels alongside the caller's *live*, currently-presented JWT, never a cached identity or a cached ownership assumption — the owning service's own per-resource check is the sole actual gate (requirement-spec §5, ADR-0028, edge-cases.md's mid-session-account-switch case).
- **Idempotency: the same `(session, intent, slots-hash)` tuple within its replay window returns the original attempt's outcome, never re-executes.** Formalized as `ShoppingAssistantIdempotencyKey`'s uniqueness-per-scope invariant and its "reuse, never re-mint" rule, mirroring `kart-payment-service`'s own `IdempotencyRecord` invariant exactly (requirement-spec §5).
- **This service's aggregates never reference another service's aggregate by anything richer than an opaque foreign identifier.** Formalized as `ExternalResourceReference`'s own closed `{ resourceType, resourceId }` shape (see its dedicated reasoning section above) — no embedded `Order`/`Cart`/`Product` sub-object ever persists on `ShoppingAssistantSession`, `ShoppingAssistantAuditRecord`, or `ShoppingAssistantIdempotencyKey` anywhere in this model (ADR-0028).

## Cross-Aggregate Interaction

A single mutating turn touches all three aggregates, but never in one transaction — they live in different stores, or at materially different points in time around a non-transactional external call:

1. **Acquire the per-session lock; read `ShoppingAssistantSession` (Redis), if `sessionId` is supplied.** Serializes this turn against any other in-flight turn for the same session (edge-cases.md's concurrent-duplicate-turn decision) — the existing `lastResolvedIntent`/`pendingConfirmation` (if present and not expired) become this turn's interpretation context.
2. **Model-Gateway plan/confirm calls; build and validate a `QueryPlan`-shaped intent→endpoint resolution (transient, not persisted independently — mirrors the sibling's own `QueryPlan` treatment).** None of this touches any aggregate directly.
3. **If the resolved intent is mutating and FR-004 confirmation is affirmed: reserve a `ShoppingAssistantIdempotencyKey` row (Postgres) for this attempt's scope — insert-if-absent; if a matching scope already exists, reuse its stored `mintedKeyValue` instead of minting a new one.** This is the first durable write, and it happens *before* the downstream call.
4. **Fire the downstream mutating call, carrying the reserved/reused `Idempotency-Key` header and the caller's live, currently-presented JWT** (never a value read from `ShoppingAssistantSession`).
5. **Write `ShoppingAssistantAuditRecord` (Postgres) — a single insert, this turn's own new `ShoppingAssistantTurnId` — always, regardless of outcome.** This is the one durable, append-only fact every turn produces, referencing the `ShoppingAssistantIdempotencyKey`'s scope by value (an opaque correlation, not a hard cross-aggregate foreign-key requirement — the same "correlated by value, not by mandatory FK" pattern `kart-payment-service`'s own three aggregates already use among themselves).
6. **Upsert `ShoppingAssistantSession` (Redis) — overwrite `lastResolvedIntent` wholesale and clear/set `pendingConfirmation` in the same write, refreshing the sliding TTL. Release the per-session lock.**

Steps 3, 5, and 6 are writes to two independent stores (Postgres for 3/5, Redis for 6), coordinated only by the per-session lock acquired in step 1 (which guarantees no second turn for the same session interleaves) — never a two-phase commit. A crash between step 5 and step 6 leaves a durable, correct `ShoppingAssistantAuditRecord` for the turn that did complete, with `ShoppingAssistantSession` simply not advancing — the next turn is then interpreted against the *previous* turn's intent, a stale-but-not-corrupt outcome no worse than the session having idle-expired outright, tolerated by the same TTL/expired-session handling already in place.

## Modeling Decisions & Assumptions (Resolved Here, Not Escalated — Engineering Defaults, Revisable)

1. **Exactly three aggregate roots, matching ADR-0028's ownership ceiling exactly, not padded beyond it.** `ShoppingAssistantSession` (Redis), `ShoppingAssistantAuditRecord` (Postgres), `ShoppingAssistantIdempotencyKey` (Postgres) — no fourth aggregate, no `Order`/`Cart`/`Product`-shaped structure, anywhere in this model.
2. **`pendingConfirmation` lives inside `ShoppingAssistantSession`'s own consistency boundary, not as a separate Redis-native aggregate** — see the dedicated Modeling Decision above; the deciding factor is the atomic-clear-on-new-resolution invariant, not the fields' differing TTLs.
3. **`ShoppingAssistantIdempotencyKey` is modeled as its own aggregate, not a field on `ShoppingAssistantAuditRecord`** — resolving design-decisions.md's own explicitly deferred question, using the identical reserve-before-external-call reasoning `kart-payment-service/ddd-model.md`'s Modeling Decision #2 already established.
4. **Three glossary-collision renames** (`ShoppingAssistantSession`, `ResolvedShoppingIntent`, `ShoppingAssistantAuditRecord`, and `ShoppingAssistantIdempotencyKey`) — see Naming Notes above. This document treats the rename as a glossary-ownership fix only; no already-approved schema/column/Redis-key name from `design-decisions.md`/`architecture.md` is asked to change.
5. **A single generic `ExternalResourceReference` value object, not five separately-named ones** — the invariant enforced (opaque id + type tag, never a richer sub-object, never locally validated for ownership) is identical across `orderId`/`cartId`/`addressId`/`sku`/`couponCode`, so one shape with a discriminator is the more honest model than five near-duplicate value objects.
6. **No masked-payment-reference value object is modeled** — the underlying default-payment-method concept (intent row 9) is itself a confirmed, unresolved gap (Data-2); modeling structure for data no endpoint yet exposes would be building ahead of a requirement that doesn't exist yet (mirrors `kart-payment-service/ddd-model.md`'s own restraint on chargeback-lifecycle depth, and ADR-0026's "no speculative placeholder" discipline).
7. **`ShoppingAssistantSession` is modeled as Redis-backed, not Postgres-backed** — resolving the inherited `design-decisions.md`/`architecture.md` inconsistency described above in favor of `design-decisions.md`'s dedicated, reasoned decision.
8. **No internal or external domain events are proposed for any aggregate** — mirrors `kart-ai-assistant-service/ddd-model.md`'s Modeling Decision #3 and architecture.md/requirement-spec §9 item 4's zero-async-edges ruling; every step within a turn (translate → validate → confirm → execute → summarize → persist) is a direct, synchronous, in-process sequence, not an event-driven one.
9. **The Intent Catalog is referenced, never modeled as this service's own aggregate** — see its dedicated section above; it is external-to-the-domain-model application config with no per-instance identity, no write path, and no lifecycle beyond ordinary code review/redeploy.
