# Design Decisions: kart-shopping-assistant-service

Cross-cutting technology/design-pattern choices this service's requirement-spec.md and edge-cases.md force, working from the fixed guarantees ADR-0028/0029/0030 already closed. Service boundaries (ADR-0028), RBAC scope mechanism (ADR-0029), and the FastAPI/Python stack policy (ADR-0030) are not re-litigated here — each decision below builds on top of those rulings. Service/aggregate boundaries, domain model, and schema/table design are left to the Architecture, DDD, and Database Design Agents that follow.

## Decision: Web Framework / ASGI Server

- **Requirement driving this:** ADR-0030 (FastAPI accepted at the policy level; ASGI server left to this stage); requirement-spec.md §4 NFR row "Scalability" ("stateless orchestration layer, horizontally scalable per the platform default") and "Availability" (99.9% secondary tier, §9 item 1).
- **Options considered (3):** Bare Uvicorn (single-process asyncio ASGI server) run directly · Gunicorn as a process manager with `uvicorn.workers.UvicornWorker` (multi-process, one worker per core, supervised/restarted by Gunicorn) · Hypercorn (HTTP/2-capable ASGI server)
- **Decision (3-5 bullets max):**
  - Chosen: Gunicorn + `uvicorn.workers.UvicornWorker`, one process per container replica's allotted core(s), scaled horizontally across container replicas (per the platform's existing scaling default) rather than scaled vertically via a single bare Uvicorn process.
  - Why: Gunicorn adds worker-process supervision (restart-on-crash, graceful worker recycling) that a bare Uvicorn process lacks — the closest Python-native analogue to Kestrel's own multi-worker robustness inside the platform's .NET services — and is FastAPI's own documented production recommendation; Hypercorn's HTTP/2 capability answers a need (browser-initiated HTTP/2) this service, sitting behind the Gateway per ADR-0028, does not have.
  - Trade-off accepted: an added process-management layer (container orchestrator restarts the container; Gunicorn additionally restarts a hung worker inside it) versus bare Uvicorn's single-process simplicity — accepted because a hung single event loop inside one container is otherwise invisible to a liveness probe until the whole container is killed, a slower failure-detection path than Gunicorn's own worker heartbeat.

## Decision: Structured-Output / Tool-Calling Enforcement

- **Requirement driving this:** requirement-spec.md §8 ("structured-output/function-calling... required as a safety control, not merely a determinism nicety, because this service's LLM output can trigger a mutating call"); FR-002 ("deterministic application code — never the LLM — validates the model's structured-output intent against the registered catalog"); edge-cases.md "Confirmation or Summary Text Implies a Capability That Doesn't Exist" (grounding check extended backward to FR-004 confirmation text, not only FR-006 summaries).
- **Options considered (3):** Prompt-engineering-only (instruct the model to emit JSON, parse the raw string, trust it) · Pydantic v2 models as the canonical per-intent schema, requested from the Model Gateway via its structured-output-capable tier (no library/vendor named), with every returned payload re-validated server-side against the Pydantic model before FR-002's catalog gate runs · A third-party structured-output wrapper library (e.g. an "Instructor"-shaped tool) layered directly on a named provider SDK
- **Decision (3-5 bullets max):**
  - Chosen: one Pydantic v2 model per catalogued intent (§2) as the single source of truth for that intent's slot shape, requested from the Model Gateway abstraction (see the Model-Gateway decision below) via a structured-output-capable tier request — never a vendor-specific call — and mandatorily re-parsed with `.model_validate()` server-side on receipt, before FR-002's catalog-validation gate runs; a payload that is syntactically valid JSON but fails Pydantic validation is treated as an unresolved/ambiguous slot (FR-008 clarification), never coerced or silently accepted.
  - Why: Pydantic is Python's de facto schema-validation standard and directly operationalizes FR-002's "structured-output intent" language; requesting via the Model Gateway's own capability flag (not a named library specific to one provider's constrained decoding) keeps this consistent with §8's provider-agnostic mandate; because this is a **safety control** (§8) and not just a determinism nicety, trusting only the provider's own constrained-decoding guarantee without an independent server-side re-validation would be a weaker guarantee than a plain vendor SDK call with manual parsing — the double-check is the deliberately stronger posture this risk class demands.
  - Trade-off accepted: one Pydantic model must be authored and kept in lockstep with each catalog row in §2, and a genuinely edge-provider response that violates the schema is rejected rather than best-effort-repaired — accepted because FR-002 already requires this schema/catalog correspondence to exist as reviewable application config, and a "best-effort repair" of a schema violation is precisely the kind of silent-guess FR-008 forbids.

## Decision: `kart_shared` Auditing Equivalent (ADR-0030 Guarantee Row 1)

- **Requirement driving this:** ADR-0030's guarantee table row 1 (audit fields "enforced at the ORM/data-access layer... not by convention/discipline in application code"); requirement-spec.md §6 (one audit record per turn, necessarily including `created_by`/`updated_by`-shaped provenance); ADR-0028's data-ownership table (`ConversationSession`, `AuditRecord` are this service's only owned aggregates).
- **Options considered (3):** Application-code discipline — every write path manually calls a `set_audit_fields()` helper before persisting · A SQLAlchemy ORM-level event hook (a `before_flush` Session event, registered once in `kart_shared.auditing`) that reads the resolved principal from a `contextvars.ContextVar` populated by a FastAPI request-scoped dependency, and stamps `created_at`/`updated_at`/`created_by`/`updated_by` on every mapped mutable model automatically · A PostgreSQL trigger function performing the same stamping at the database layer, independent of the ORM
- **Decision (3-5 bullets max):**
  - Chosen: a SQLAlchemy `before_flush` Session event hook, packaged once in `kart_shared.auditing` (the Python-native equivalent of `Kart.Shared.Auditing`'s `SaveChangesInterceptor`), reading the resolved principal from a request-scoped `contextvars.ContextVar` set by a FastAPI dependency at the top of every request — no handler/repository code calls an audit helper manually, and no audit field is ever accepted from client-supplied request data.
  - Why: ADR-0030 requires this to be "enforced at the ORM/data-access layer... not by convention," which a `before_flush` hook satisfies exactly the way `SaveChangesInterceptor` does on the .NET side — one hook, wired once at Session-factory construction, impossible to skip by forgetting to call a helper in a new handler; this is the direct Python-native parity mechanism ADR-0030 asks for, not a weaker best-effort substitute.
  - Trade-off accepted: this hook only fires for ORM-mediated writes through the SQLAlchemy `Session` — a raw SQL statement issued outside that `Session` would bypass it, exactly the same limitation `SaveChangesInterceptor` has for anything bypassing EF Core's `DbContext` (parity, not a weaker guarantee); this service's own coding convention must never issue raw SQL for a mutating write, the same discipline the .NET fleet already assumes for its own interceptor to hold.

## Decision: RabbitMQ Manifest-Declaration Equivalent (ADR-0030 Guarantee Row 2) — Documented, Not Built

- **Requirement driving this:** ADR-0030's guarantee table row 2 ("not required at all unless a future pass... determines this service needs any publish/consume relationship — resolved as zero for v1, so this equivalent is a documented-but-unbuilt pattern until that changes"); requirement-spec.md §9 item 4 (zero events consumed/published for v1, mirroring ADR-0024's own zero-async-edges ruling for the sibling).
- **Options considered (2):** Build nothing and document nothing, deferring the entire question to whenever an event edge is first needed · Document (but do not build) the intended pattern now: a Python startup hook in `kart_shared.messaging`, using `aio-pika` (an async-native RabbitMQ client) to read the platform's existing JSON manifest schema (`kart-requirements.md` §8/§9) and idempotently declare exchange/queue/DLX/retry-ladder topology at startup, identical in shape to the .NET convention
- **Decision (3-5 bullets max):**
  - Chosen: document the pattern now, build nothing. If a future pass ever adds a publish/consume edge to this service, the Python-native equivalent is a `kart_shared.messaging` startup hook using `aio-pika` to read the same, already-language-agnostic JSON manifest schema every other service already declares against.
  - Why: ADR-0030 itself frames this row as "documented-but-unbuilt," not "build a substitute now" — requirement-spec.md §9 item 4 has already, independently, resolved this service's event consumption/publication at zero for v1; `aio-pika` is named (over a blocking client such as `pika`) because this service's runtime is natively async (Uvicorn/FastAPI, per the Web Framework decision above), and a blocking client would require a thread-pool bridge for no benefit over a client built for the same event loop.
  - Trade-off accepted: no working code exists for this today; if an event edge is ever added, the manifest schema's actual current shape must be re-confirmed against `kart-requirements.md` §9 at that time rather than assumed unchanged from this document's writing.

## Decision: RLS-Equivalent Enforcement (ADR-0030 Guarantee Row 3)

- **Requirement driving this:** ADR-0030's guarantee table row 3, explicitly framed as "more a 'confirm and configure' item than a 'build a substitute' item" since Postgres RLS is database-native, not EF-Core-native; requirement-spec.md §5 domain invariant ("no cross-customer action... enforced by forwarding the caller's own JWT... so that service's own per-resource ownership check... is what actually gates the mutation") applied here to this service's own two owned tables (`conversation_session`, `audit_record`, and the idempotency-key table below).
- **Options considered (3):** No RLS — enforce ownership purely via an application-level `WHERE owner_id = :principal` clause added manually to every query · Native PostgreSQL `CREATE POLICY` row-level-security policies on `conversation_session`/`audit_record`/`idempotency_keys`, with the resolved principal set as a Postgres session/transaction-local variable (`SET LOCAL app.current_principal = ...`) at the start of every request-scoped transaction, via a SQLAlchemy connection/transaction-begin hook · Row-level filtering enforced only at the SQLAlchemy query-construction layer (a shared base-query helper that always appends `.filter(owner_id == principal)`)
- **Decision (3-5 bullets max):**
  - Chosen: confirmed reasoning — native PostgreSQL RLS policies on this service's own tables, since RLS enforcement itself is a database-native guarantee independent of which language's driver connects (ADR-0030's own framing, correct as stated). The concrete Python-side mechanism: a SQLAlchemy engine-level hook (a `checkout`/`begin` event, wired once in `kart_shared.db`) issues `SET LOCAL app.current_principal = '<resolved-principal-id>'` as the first statement of every request-scoped transaction, reading the same `contextvars`-resolved principal the auditing hook (above) already reads — the RLS policy's `USING (owner_customer_id = current_setting('app.current_principal')::uuid)` clause then reads that session-local variable.
  - Why: this is a "confirm and configure," not a "build a substitute" item exactly as ADR-0030 frames it — Postgres itself enforces the policy regardless of language; the one genuinely new Python-side piece is reliably setting the session variable per transaction, which a connection/transaction-lifecycle event hook (not per-query application code, which could be forgotten on one path) provides, mirroring the same "resolve principal once, inject everywhere" intent behind EF Core's `ICurrentPrincipalAccessor` without needing an EF-Core-specific mechanism.
  - Trade-off accepted: `SET LOCAL` is transaction-scoped and must be re-issued on every new transaction/connection checkout — if SQLAlchemy's connection-pool reset behavior (`reset_on_return`) is misconfigured, a stale session variable could theoretically persist across a pooled connection's reuse; correct pool-reset configuration is flagged forward as an Architecture/Database Design Agent-level implementation item, not a number invented here.

## Decision: Idempotency-Key Persistence

- **Requirement driving this:** requirement-spec.md §5 domain invariant ("generates and persists one idempotency key per attempted mutating action within a conversation turn and reuses it on any internal retry... following the platform's existing pattern — `kart-order-service`'s and `kart-payment-service`'s own `Idempotency-Key` header convention"); edge-cases.md "Concurrent/Duplicate Mutating Turns" (per-session serialization closes the *concurrent*-duplicate case, but a persisted key is still separately required for a *sequential* retry of the same attempted action, which serialization alone does not address).
- **Options considered (3):** No persistence — mint a fresh key in-memory per call attempt, relying only on session serialization · A dedicated Postgres table (SQLAlchemy model), mirroring `kart-payment-service`'s own `idempotency_keys` unique-constraint table shape, scoped to this service's own attempted mutating actions · An ephemeral Redis-backed key store with TTL, reusing the same Redis deployment as session/breaker state
- **Decision (3-5 bullets max):**
  - Chosen: a dedicated Postgres table, `idempotency_keys` (via SQLAlchemy), directly mirroring `kart-payment-service`'s own unique-constraint pattern — one row per attempted mutating action, unique constraint on `(conversation_session_id, intent_name, resolved_slots_hash)`; the key is generated on first attempt and the same stored key is returned (never re-minted) on any retry whose scoping tuple matches, then forwarded as the `Idempotency-Key` header on the downstream mutating call (order-cancel, cart-checkout, offer-apply, etc.).
  - Why: requirement-spec.md §5 explicitly names this as following `kart-order-service`'s/`kart-payment-service`'s own existing header convention — reusing that exact table shape via SQLAlchemy is the direct Python-native equivalent rather than inventing a new mechanism; Postgres (not Redis/TTL) is appropriate because the retry this guards against (e.g. a customer re-confirming after a slow network round trip or a page reload) needs durability across a gap that could exceed a short ephemeral TTL, unlike the purely session-scoped state in the Confirmation-State-Machine decision below.
  - Trade-off accepted: this adds one more table beyond the two aggregates (`ConversationSession`, `AuditRecord`) ADR-0028's ownership table names explicitly — this document treats it as an audit-adjacent structure (recording *attempts*, the same class of fact `AuditRecord` already exists to capture), not a new domain-data ownership violation, but whether it is modeled as its own table or a field set on `AuditRecord` is schema/aggregate design left to the DDD Agent, not decided here.

## Decision: Bounded Tool-Calling Registry

- **Requirement driving this:** requirement-spec.md §2 (the closed, enumerable 12-row intent catalog); FR-003 ("Execute only via a fixed, versioned intent→endpoint mapping table (application config, never LLM-authored)... routed to FR-010, never attempted against a nonexistent endpoint" for confirmed gaps rows 8/10); ADR-0028's explicit nine-peer fan-out allowlist (order, cart, offer, search, product, recommendation, user, delivery-tracking, wishlist — `kart-payment-service` never called directly).
- **Options considered (3):** One large `if`/`elif` dispatch function switching on intent name · A decorator-based static registry (`@intent_handler("<intent_name>")`) mapping each catalog intent to a handler declaring its own Pydantic schema (see Structured-Output decision), its one downstream API client, and its mutating/read-only flag — built once into a frozen dict at process import time, with a startup assertion that every §2 row has exactly one handler and no handler references an unlisted intent · A runtime plugin-discovery system scanning arbitrary modules for decorated handlers dynamically
- **Decision (3-5 bullets max):**
  - Chosen: the decorator-based static registry, `@intent_handler("<intent_name>")`, eagerly registered at import time into one frozen `INTENT_REGISTRY: dict[str, IntentHandler]`, never mutated at runtime and never dynamically discovered; each handler wires exactly one of the nine allowlisted downstream clients (no client for `kart-payment-service` is ever instantiated anywhere in the registry); a startup-time assertion fails the process if any §2 catalog row lacks a registered handler, or if a handler declares an intent name outside §2.
  - Why: FR-003's "fixed, versioned intent→endpoint mapping table (application config, never LLM-authored)" is best satisfied by a registry that is closed and fully enumerable at import time — reviewable as a single diff, exactly like any other config — rather than a runtime-discovered plugin system, which would let a handler be hot-added without the same review path; a decorator pattern keeps each handler's mapping declaration co-located with its implementation, avoiding the single unreviewable dispatch function a growing intent catalog would otherwise produce; ADR-0028's "never `kart-payment-service` directly" rule is enforced structurally (no such client exists in the registry) rather than only by a runtime check that could be bypassed by a future careless addition.
  - Trade-off accepted: adding a new intent requires a code change and redeploy — there is no live-editable routing table — accepted as the direct, intended consequence of FR-003's "never LLM-authored" mandate; a dynamic plugin-discovery alternative would technically permit exactly the kind of unreviewed routing change FR-003 exists to prevent.

## Decision: Confirmation-Before-Mutation State Machine

- **Requirement driving this:** edge-cases.md "Follow-up Message That Should Reset vs. Carry Forward a Pending Mutating Confirmation" (default: discard on any newly (re-)resolved intent, never silently carry forward); FR-007 ("a pending mutating confirmation is never silently carried forward across a topic switch... a fresh FR-004 confirmation is always required"); requirement-spec.md §5's own restating of this as a standing domain invariant.
- **Options considered (3):** Client-side only — the pending confirmation lives solely in the message history the client resends each turn, with no server-side persistence · A Redis-backed record, key-namespaced per session (`shopping-assistant:session:{sessionId}`), holding a distinct `pending_confirmation` field (the intent name + resolved slots the FR-004 confirmation text was generated from) with its own short TTL, independent of and shorter than the broader conversation-context TTL, explicitly cleared to null the instant FR-002 resolves any new intent in a later turn (not left to passive TTL expiry alone) · A Postgres-backed pending-confirmation row, polled/checked per turn
- **Decision (3-5 bullets max):**
  - Chosen: the Redis-backed record, mirroring `kart-ai-assistant-service/design-decisions.md`'s own Conversation-Session-Storage precedent (same Redis deployment, same "ephemeral, TTL-bound, per-key, no cross-key relational structure" profile) rather than introducing a second storage technology for structurally the same kind of state; the `pending_confirmation` field is a distinct, narrower field from the broader "last resolved intent/slots" conversational context, with its own shorter TTL, and — critically — is explicitly cleared the instant a new intent is (re-)resolved in a later turn, not merely left to expire naturally.
  - Why: the requirement is explicitly server-side authoritative (FR-004's confirmation gate is an application-code control, not a client-trusted one) — a client-side-only store (option 1) would let a compromised or malicious client resurrect a confirmation the server itself already discarded, directly violating the "never silently carried forward" invariant; reusing Redis (already justified for session state on this platform) avoids standing up a second coordination store for what is the same kind of ephemeral, per-session data.
  - Trade-off accepted: requires two related-but-distinct Redis fields per session rather than one unified blob, and requires the explicit clear-on-new-resolution step to fire correctly on every turn rather than relying on TTL alone — a small added piece of state-machine logic, accepted because TTL expiry alone cannot express "discard immediately on topic switch, even well within the TTL window," which is exactly what the edge case requires.

## Decision: Prompt-Injection Structural Firewall

- **Requirement driving this:** edge-cases.md "Prompt Injection via Product Description/Review Surfaced During Discovery/Compare" — resolved as structured-output/bounded-tool-calling containment (already covered above) **plus** "a Discovery/Compare turn's content-summarization step is never wired to the tool registry's mutating entries at all, regardless of what the fetched text contains"; requirement-spec.md §5 ("the consequence class here is categorically worse since this service can act").
- **Options considered (3):** Prompt-engineering-only defenses (instruct the model to disregard embedded instructions in fetched content) · A single shared codebase with a runtime role/permission check gating which tools a given code path may invoke · Hard module-boundary separation: a `read_summarization` module (Discovery/Compare/general-Q&A response generation) that has zero import statement — direct or transitive — reaching the mutating-intent registry or any mutating downstream client, enforced by an architectural import-linter rule in CI (e.g. `import-linter`) that fails the build on any dependency edge from summarization code into the mutation registry
- **Decision (3-5 bullets max):**
  - Chosen: hard module-boundary separation, enforced at import level and checked in CI by an import-linter rule — the content-summarization code path for read-only intents cannot reach the mutating tool registry (or any of its downstream clients) through any import chain, and this is verified automatically on every build, not only by code review.
  - Why: edge-cases.md is explicit that the control this service specifically needs (beyond what the read-only sibling's containment-only defense provides) is structural — "no code path capable of invoking any mutating tool-registry entry, regardless of what the fetched text contains"; a runtime permission check (option 2) still leaves a single shared codebase where a future refactor could accidentally wire the two together, and only a test (which could be skipped or miss a new code path) would catch it — an import-level architectural boundary makes that mistake a build-time failure instead, a strictly stronger, "can't accidentally happen" guarantee.
  - Trade-off accepted: any logic genuinely shared between the two sides (e.g. resolving a product SKU, needed by both a read-only Compare response and a mutating Add-to-Cart-from-recommendation handler) must be factored into a third, dependency-free shared utility module neither side imports from the other's side — a small added module-layout discipline, accepted as the direct cost of a structural rather than merely disciplinary firewall.

## Decision: Per-Downstream-Service Circuit Breaker

- **Requirement driving this:** requirement-spec.md §9 item 5 ("adopts per-edge-independent circuit breakers for each of its downstream synchronous dependencies... the same resilience pattern `kart-admin-service`'s own comparably wide synchronous fan-out already uses"); ADR-0028's nine-peer fan-out enumeration; edge-cases.md "Downstream Partial Outage Mid-Composed-Intent (`kart-offer-service` Down During Coupon-Then-Checkout)."
- **Options considered (3):** `aiobreaker` (an asyncio-native circuit-breaker library, in-process state only) · `purgatory` (an async-first circuit-breaker library with pluggable, shareable state backends including Redis) · A hand-rolled per-edge breaker class (a simple closed/open/half-open state machine, in-process only)
- **Decision (3-5 bullets max):**
  - Chosen: `purgatory`, with one named circuit-breaker instance per downstream peer (nine total: order, cart, offer, search, product, recommendation, user, delivery-tracking, wishlist), configured with a Redis-backed shared state store (reusing the same Redis deployment as the Confirmation-State-Machine decision above) so breaker state is consistent across horizontally-scaled replicas.
  - Why: requirement-spec.md's own Scalability NFR mandates a stateless orchestration layer, horizontally scaled per the platform default — an in-process-only breaker (either `aiobreaker`'s default backend or a hand-rolled state machine) would let each replica independently and inconsistently decide a given peer is healthy, so one replica could trip its breaker while another keeps hammering an already-struggling peer; `purgatory`'s async-native design matches this service's FastAPI/Uvicorn request path and ships a Redis adapter out of the box, avoiding the need to invent a bespoke distributed-state mechanism.
  - Trade-off accepted: adds a runtime dependency on Redis for breaker-state consistency (beyond its existing session-state use) — a Redis outage degrades to independent per-replica breaker behavior (each replica falls back to its own local view) rather than causing a hard failure, mirroring the same Redis-dependency trade-off `kart-ai-assistant-service/design-decisions.md` already accepts for its own Redis-backed mechanism. Numeric trip thresholds/timeouts remain explicitly deferred to the Architecture Agent (requirement-spec.md §9's own non-blocking list) — not invented here.

## Decision: Model-Gateway Abstraction

- **Requirement driving this:** requirement-spec.md §8 ("Provider-agnostic via a model-gateway abstraction, matching `kart-ai-assistant-service`'s own posture: no named vendor/model anywhere in this document's requirements") and §7's integration table ("Model Gateway (LLM provider) — New, provider-agnostic").
- **Options considered (3):** Call a named vendor SDK directly, with provider selection as an internal branch (explicitly forbidden by §8) · Implement a bespoke, service-local Python client hardcoded against whichever vendor is eventually configured, with capability-flag branching embedded in this service's own application code · Implement a new, thin, provider-agnostic Python model-gateway client (a `ModelGatewayClient` interface exposing `complete()`, `supports_structured_output()`, `supports_tools()`, `context_window()`) requesting a capability **tier**, never a vendor/model, mirroring the interface shape `kart-ai-assistant-service/design-decisions.md`'s own Model-Gateway decision already established for the platform's .NET side
- **Decision (3-5 bullets max):**
  - Chosen: the third option — a new, thin Python model-gateway client module, packaged inside the shared `kart_shared` Python package (ADR-0030) rather than duplicated ad hoc inside this service, so a future second Python service inherits the same adapter instead of re-deriving it; it exposes the same conceptual capability-flag/tier-routing contract the .NET-side Model Gateway pattern already establishes, requesting e.g. a "structured-output-capable" tier for the plan/confirm calls and a cheaper/faster tier for the summarization call — never a vendor or model name, anywhere in this document or in application code.
  - Why: §8 forbids naming a vendor exactly as strongly here as for the sibling service; the capability-flag/tier-routing shape is an already-approved, working pattern for the equivalent problem on the .NET side — porting that shape (not just the general idea of "some abstraction") avoids producing two structurally incompatible mental models for what should be one platform-wide concept, even though no in-process code can be shared across the language boundary; this is explicitly new Python infrastructure with no prior Python-native art on this platform, as this pipeline stage was told at the outset, so it is designed once, in `kart_shared`, rather than once per call site.
  - Trade-off accepted: because this is genuinely new infrastructure, the client's actual transport to the underlying Model Gateway component (HTTP vs. gRPC) and its tier→provider routing config format still need their own build effort this document does not fully specify — flagged forward as an Architecture Agent-level integration ticket; the *pattern* (capability-tier request, no vendor naming, shared-package placement) is decided here, the wire protocol is not.
