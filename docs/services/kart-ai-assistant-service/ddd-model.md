# DDD Model: kart-ai-assistant-service

**Pipeline-order note.** This is the first `ddd-model.md` pass for this service — unlike `kart-analytics-service`/`kart-admin-service`'s own DDD models, which formalized an already-built `database-design.md`/`event-contract.md` written under a "narrow enough to skip DDD" precedent, `kart-ai-assistant-service` has no pre-existing schema to reconcile against; the Database Design Agent runs after this document, not before it. This model is therefore the first place this service's aggregate boundaries are made concrete, not a formalization of prior art.

**Input-freshness note.** `requirement-spec.md`, `edge-cases.md`, `design-decisions.md`, and `architecture.md` are all `status: approved`, each carrying its own `approval_note` explaining that the remaining open items (Business-1 revenue gross/net, UX-1 session TTL, UX-2 default date range, Infrastructure-1 latency/cost budgets) are non-blocking for this pipeline stage — they gate business sign-off and production-readiness, not aggregate/entity/value-object modeling. This document does not invent numeric values for any of them; it models the aggregates to be agnostic of the exact numbers (see ConversationSession below).

## Boundary Summary

`kart-ai-assistant-service` is, in DDD terms, an **orchestration/control-plane caller** of `kart-analytics-service`'s data (architecture.md's Boundary Rationale, itself a direct analogy to `kart-admin-service`'s own relationship to Product/Category/Offer/Identity/Inventory, per ADR-0024) — just read-only instead of write-through, and single-dependency instead of five-way fan-out. It owns no Core-domain aggregate and asserts no write authority over any other service's state anywhere on the platform (requirement-spec §1, §4).

**Its bounded context is exactly two local aggregates, closed by ADR-0024 and restated here as this document's own confirmed shape, not re-derived:**

1. **`ConversationSession`** — the last resolved structured intent per conversation, the authoritative state a follow-up turn is interpreted against (source spec §14.1).
2. **`AuditRecord`** — one immutable, append-only record per turn (successful, clarification, or error), per source spec §20 (FR-011).

**Nothing else.** In particular — and this is the single most important invariant this document must visibly honor — **no `Product`, `Order`, `Revenue`, or any other analytics-shaped aggregate exists anywhere in this model.** ADR-0024's data-ownership table is explicit and binding: this service "may never own... any copy of Analytics' dashboard/read-model data (revenue, orders, product performance, etc.)," "any copy of Order/Product/Inventory/User domain data," or "a cache or local recomputation of a number Analytics itself already returns." Every number this service ever surfaces is fetched live from `kart-analytics-service` at query time (FR-003) and is never durably stored here in any of the two aggregates below — confirmed field-by-field in each aggregate's definition (neither aggregate has a field that holds a metric value, a row of dashboard data, or a business figure of any kind; only counts, parameters, and metadata about a query that was run). A future pass over this file that ever introduces such a field would be reopening a decision ADR-0024 already closed, not an incremental addition this document's own authority covers.

Two aggregate roots below, each with a materially different storage technology, lifecycle, and transaction boundary — confirmed by the transaction-boundary test (`ddd-agent.md`/`ddd-cqrs-standards.md`): a `ConversationSession` write (an ephemeral, single-mutable-slot upsert to Redis, TTL-bound) and an `AuditRecord` write (a durable, append-only insert that must remain queryable long after the session it describes has expired) can never be one transaction, because they don't even share a datastore. See Cross-Aggregate Interaction below.

## Aggregate: ConversationSession

**Entity:** `ConversationSession` — identified by `ConversationId` (value object; the `conversationId` the client supplies or is issued on first turn, per §21.1's request shape `{ conversationId?, message }`). Backed by Redis, key `ai-assistant:session:{conversationId}` (design-decisions.md, "Conversation-Session Storage"; architecture.md's Deployment/Scaling Posture) — not a PostgreSQL/MongoDB table, a deliberate deviation from the pattern `kart-analytics-service`/`kart-admin-service`'s own aggregates use, justified by that decision already being closed (session/raw-transcript state is "eventually-irrelevant local state," ADR-0024's ownership table, not business data warranting Postgres's durability/transactional guarantees).

**Naming note — resolves a potential collision with `kart-identity-service`'s own "Session" term.** `docs/ddd/ubiquitous-language.md` already owns the bare term **Session** for Identity's login-to-logout/revocation lifecycle of a refresh-token rotation family (`kart-identity-service`). This service's conversation-context concept is unrelated — no token, no login/logout lifecycle, no refresh-token rotation — and is deliberately named **`ConversationSession`**, never bare "Session," to avoid exactly that ambiguity. See the ubiquitous-language.md update below, which states this explicitly rather than silently reusing an overloaded name.

**Value objects:**
- `ConversationId` — the opaque session identifier scoped to one chat-panel instance (source spec §14.1); generated by this service on the first turn of a new conversation, supplied by the client on every subsequent turn. Never reused across two logically distinct conversations.
- `ResolvedIntent` — the canonical structured intent (source spec §8's JSON schema). See "Value Object: ResolvedIntent — Reasoning" below for why this is modeled as a value object, not an entity with its own identity, despite also appearing (by value) on `AuditRecord`.
- `TurnProvenance` — `{ isProvisional, reconciledThrough }`, the eventual-consistency signal Analytics' own `DashboardEnvelope` carries (FR-012), persisted here specifically so a later turn's freshly-fetched provenance can be compared against the prior turn's (edge-cases.md, "Follow-up Against Data That Has Since Changed"). This is the "modest addition within the two-aggregate boundary" design-decisions.md's Redis decision already names.

**Fields:** `conversationId: ConversationId`, `lastResolvedIntent: ResolvedIntent` (nullable — absent before the conversation's first turn resolves), `lastTurnProvenance: TurnProvenance` (nullable, mirrors `lastResolvedIntent`'s presence), `lastActivityAt` (the timestamp the sliding-window idle timer is computed from — design-decisions.md's "TTL implemented via Redis's native key expiry with sliding refresh on every turn").

**Invariants:**
- **Exactly one mutable "current" resolved intent per session, never a history.** A follow-up turn overwrites `lastResolvedIntent` wholesale with the newly-resolved intent (fields the new message didn't address are carried forward unchanged into the *new* value, per FR-007) — this aggregate never accumulates a list of past intents; the full sequence of intents a conversation passed through is reconstructable only from the append-only `AuditRecord` trail (each turn's `AuditRecord.resolvedIntent` is that turn's own immutable snapshot), never from this aggregate itself. This is the DDD-terms restatement of source spec §14.1: "the last resolved structured intent... not the raw chat transcript, is the state a follow-up is interpreted against."
- **TTL-agnostic of the exact idle duration.** The aggregate's own existence is bounded by a sliding idle window (edge-cases.md, "Conversation Session Expiry Mid-Conversation") whose concrete duration is UX-1 — an explicitly open, non-blocking human decision (requirement-spec §8) this model does not invent a number for. The invariant this model fixes is structural, not numeric: once the idle window elapses, the aggregate must be treated as absent (concretely: the Redis key has expired), and no follow-up may be resolved against an absent session — an orphaned follow-up fragment ("only Electronics" with no prior intent) must surface a distinguishable expired-session error, never be silently interpreted as if `lastResolvedIntent` were still present (the same "ask, don't guess" principle FR-008 applies to linguistic ambiguity, applied here to temporal ambiguity).
- **A session is per-conversation, never per-user or global.** Two concurrent conversations for the same `Admin`/`Support Agent` user are two independent `ConversationSession` instances, keyed by two different `conversationId`s — this aggregate has no notion of "this user's sessions," only "this one conversation's state."
- **Concurrency: at most one turn processed at a time per `conversationId`.** Two in-flight requests against the same `conversationId` race on this aggregate's single mutable `lastResolvedIntent` slot; per edge-cases.md's "Concurrent Requests in the Same Conversation Session" decision, this is resolved by per-`conversationId` serialization (a Redis lock external to the aggregate's own data, `ai-assistant:session-lock:{conversationId}`, design-decisions.md), not by an optimistic-concurrency version field on the aggregate itself — a losing concurrent request is rejected outright, never silently merged against a possibly-stale `lastResolvedIntent`.
- **Never holds a copy of Analytics' own data.** `lastTurnProvenance` carries only the `isProvisional`/`reconciledThrough` *signal*, never the underlying dashboard figures those flags describe — this is metadata about a query result, not the result itself, and is the only Analytics-originated information this aggregate is permitted to retain (ADR-0024).

### Value Object: `ResolvedIntent` — Reasoning

The source spec's §8 schema — `metric`, `entity`, `aggregation`, `dimensions`, `filters` (`dateRange`, `category`, `sku`, `channel`, `actionType`), `ranking` (`sortBy`, `direction`, `limit`), `comparison` (`baselineDateRange`), `visualizationHint`, `clarificationNeeded` — is modeled as a **value object**, not an entity with its own identity, for three concrete reasons:

1. **It has no lifecycle of its own to look up by id.** Nothing in this service's own API surface (§21.1) or audit query pattern (§20) ever needs to fetch "the `ResolvedIntent` with id X" independent of the turn or session that produced it — it is always accessed *through* a `ConversationSession` (as "the current one") or *through* an `AuditRecord` (as "the one this turn resolved"), never on its own.
2. **It is fully defined by its field values, and is naturally replaced wholesale, not mutated in place.** A follow-up turn doesn't edit fields on an existing `ResolvedIntent` instance — the translation step (deterministic application code, FR-007) always produces a brand-new intent value (merging forward the unaddressed fields from the prior one), which is exactly the "define equality by field values, always replace rather than mutate" behavior that marks a concept as a value object rather than an entity (`ddd-cqrs-standards.md`).
3. **It appears twice, by value, never by shared reference.** `ConversationSession.lastResolvedIntent` holds the *current* value (overwritten on the next turn); `AuditRecord.resolvedIntent` holds an independent, frozen *copy* of whatever `ResolvedIntent` was current at the moment that specific turn was processed. These are not two references to one shared object — if they were, mutating the session's copy on turn N+1 would silently corrupt turn N's already-written audit record, which would violate `AuditRecord`'s own append-only/immutability invariant (below). Duplicating the value across the two aggregates (the same pattern `Money` or `CapturedAmount` already use elsewhere in this platform's models) is the only shape consistent with `AuditRecord` needing to reconstruct exactly what was true *at that turn*, indefinitely, even after `ConversationSession` has long since expired and moved on to a different value (or ceased to exist at all).

**Sub-structure, restated for clarity (not separately named value objects unless they carry their own invariant):** `filters` and `comparison` are plain structural sub-fields of `ResolvedIntent` with no invariant beyond "shape validated against §8's JSON schema" — they are not modeled as their own named value objects here. `ranking` is the one exception: it is called out as `RankingSpec` below because it carries its own invariant (bounded against a registered endpoint's documented maximum) independent of the rest of the intent.

## Aggregate: AuditRecord

**Entity:** `AuditRecord` — identified by `TurnId` (value object; a fresh id generated once per processed turn). Backed by this service's own durable, append-only store (the concrete storage technology — PostgreSQL vs. another option — is the Database Design Agent's own call, not fixed here; what *is* fixed is that it is not Redis, since this aggregate must remain queryable after the `ConversationSession` describing the same conversation has expired — edge-cases.md's session-expiry decision is explicit that "turns outlive a session's active lifetime, needed for audit query even after the session expires").

**Modeled as its own aggregate root, not a child entity of `ConversationSession` — confirmed, not merely asserted.** Three independent reasons, each sufficient on its own:
1. **Different transaction boundary.** `ConversationSession` lives in Redis; `AuditRecord` lives in a durable store the Database Design Agent will fix — they can never be written in one ACID transaction, which is the exact test (`ddd-agent.md`) for "two aggregates, not one."
2. **Different lifecycle.** A `ConversationSession` is TTL-bound and disappears; the `AuditRecord`s it produced must not disappear with it — FR-011's audit requirement and this service's own Observability NFR (requirement-spec §3: "100% structured audit logging of every turn") both require every turn's record to remain independently queryable regardless of whether the originating session has since expired.
3. **Different identity/query pattern.** `AuditRecord` is queried by `turnId`, by `conversationId` (to reconstruct a conversation's full transcript across turns — see the ConversationSession section above), or by `userId`/date range for compliance audit (mirroring `kart-admin-service`'s `AdminActionPerformed`/`GET /admin/actions` pattern, FR-011) — none of these are natural sub-queries of "one session's current state."

**Value objects (per source spec §20's exact field list — no field invented beyond what §20 states):**
- `TurnId` — generated once per turn; this aggregate's own identity.
- `ResolvedIntent` — the same value-object shape defined above, embedded here as an immutable, frozen copy of whatever intent that specific turn resolved (or `null`/absent if the turn never reached a resolved intent — e.g., a hard validation failure before translation).
- `ClarificationDetail` — `{ question, options }` (§15.3's shape), present only when `clarificationIssued = true`.
- `TurnProvenance` — the same `{ isProvisional, reconciledThrough }` shape defined above, embedded here as this turn's own immutable snapshot (distinct instance from whatever `ConversationSession.lastTurnProvenance` may hold by the time anyone reads it later).
- `LlmLatency` — `{ planCallMs, explainCallMs }` (§20: "per LLM call — plan, explain").
- `LlmTokenUsage` — `{ plan: { promptTokens, completionTokens }, explain: { promptTokens, completionTokens } }` (§20: "prompt/completion tokens, both calls").
- `ErrorDetail` — `{ category, message }`, where `category` is one of the five FR-009/§19 response types (`unsupported | ambiguous | unauthorized | unavailable | no-data`) as extended by edge-cases.md's own two additions confirmed at that stage: a distinguishing plan-vs-explain sub-classification under `unavailable` (edge-cases.md, "LLM Provider Unavailable/Timeout"), and `expired-session` (edge-cases.md, "Conversation Session Expiry Mid-Conversation"). Zero or more per turn.
- `FinalResponseSummary` — `{ answerText, visualizationType }` (§20: "answer text + visualization type — not the full raw LLM payload, to bound log volume").

**Fields:** `turnId: TurnId`, `conversationId` (a plain reference value — see below, never a foreign key), `userId`, `role` (`Admin | Support Agent` — a reference to Identity's own coarse role claim, never redefined here), `userQuestion` (raw text, ≤ 1,000 chars per FR-001's own input bound), `resolvedIntent: ResolvedIntent` (nullable), `clarificationIssued: bool`, `clarificationDetail: ClarificationDetail` (present iff `clarificationIssued`), `toolsInvoked` (the endpoint(s) called this turn, e.g. `GET /internal/v1/dashboards/product-performance` — a list, since a period-over-period comparison issues two calls per FR-002/§5 item 4), `dataSource` (constant `"kart-analytics-service"` whenever a query executed, else absent), `queryParameters` (the `from`/`to`/`granularity`/filters actually sent — the realized parameters of that turn's `QueryPlan`, see below), `executionTimeMs` (Analytics call latency), `llmLatency: LlmLatency`, `llmTokenUsage: LlmTokenUsage`, `resultSize` (a row **count**, never the rows themselves — see the invariant below), `turnProvenance: TurnProvenance` (present iff the underlying result carried it), `groundingCheckResult` (`pass | fail`, FR-004), `errors: ErrorDetail[]`, `finalResponseSummary: FinalResponseSummary`, `timestamp`.

**Invariants:**
- **Exactly one `AuditRecord` per turn, always — successful, clarification, or error alike.** FR-011's own acceptance criterion, restated as this aggregate's own creation rule: there is no code path through this service that completes a turn (of any outcome) without writing exactly one `AuditRecord` row.
- **Append-only, immutable once written.** No field is ever updated or deleted after creation — the same posture `kart-analytics-service`'s `PiiRedactionRecord` and `kart-admin-service`'s `AdminAction` (pre-Outbox-publish fields) already hold on this platform. This is what makes the aggregate a trustworthy, reconstructable audit trail (source spec §20: "any disputed answer can be reconstructed and checked against what Analytics actually returned at that time").
- **`resultSize` is a count, never a copy of the result.** This is the field-level enforcement of ADR-0024's ownership boundary inside this aggregate specifically: `AuditRecord` may record *how many* rows a query returned, for observability, but must never store the rows/columns themselves (the `data.rows`/`data.columns` table from §13.2's response contract) — that data belongs to Analytics and is never durably re-owned here, even inside this service's own audit trail.
- **No raw LLM provider request/response body, and no `analytics_raw_events.payload` content, is ever a field on this aggregate.** Restated directly from §20's own "What is deliberately *not* logged" list and §17's PII posture — `finalResponseSummary` is bounded to answer text + visualization type specifically so the aggregate can never balloon into holding a full raw payload by accident.
- **`conversationId` is an opaque reference, never a foreign key.** `ConversationSession` (Redis) and `AuditRecord` (a different, durable store) cannot share a referential-integrity constraint across stores, and — by design — an `AuditRecord` must remain fully queryable after the `ConversationSession` it references has expired and been evicted (edge-cases.md's session-expiry decision, cited above). A dangling `conversationId` (referencing an already-expired or never-existent session) is not a data-integrity error for this aggregate; it is the expected, permanent steady state for every audit row once enough time has passed.
- **`clarificationIssued`/`errors`/`turnProvenance` are independent, non-exclusive facts about one turn, not a state machine.** A turn can (for example) carry `turnProvenance.isProvisional = true` and zero errors and no clarification, all at once — §20's field list documents independent observability facts about a single completed turn, not mutually exclusive outcome branches; the one true structural distinction this service must preserve is FR-009's "unsupported" vs. "supported, zero rows," which is captured by whether `errors` contains an `unsupported`-category `ErrorDetail`, never conflated with a normal, error-free `finalResponseSummary` that happens to describe a zero-row result.

## Value Object: `QueryPlan` — Ephemeral, Not Independently Persisted

`QueryPlan` (`{ endpoint, parameters }`, FR-002) is modeled as a value object representing the deterministic output of intent→endpoint translation — but it is **not** a field stored wholesale on either aggregate, and is not itself an aggregate. Reasoning:

- It has a genuine domain invariant worth naming: "targets exactly one registered endpoint with parameters that satisfy that endpoint's documented contract" (FR-002's own acceptance criterion), and a second validation gate exists specifically to check a resolved `QueryPlan` against its target endpoint's contract before execution (edge-cases.md, "Intent Passes Validation but the Resolved Query Plan Is Itself Malformed") — this is a real domain concept, not just a function's local variable.
- It is, however, **purely transient application state** for the duration of one turn's plan→execute→explain sequence — the platform's Caching decision (design-decisions.md) is explicit that no query result or query plan is ever cached or persisted beyond the single turn that produced it, and the registry it's built from is itself external, versioned application config (§6/§7/§10.3), not this service's own domain data.
- Its only durable trace is the *fields already on `AuditRecord`* that describe it after the fact: `toolsInvoked` (the `endpoint` half) and `queryParameters` (the `parameters` half). There is no separate, independently-persisted `QueryPlan` row anywhere — modeling one would create a third storage location for the exact same information §20 already places on `AuditRecord`, with no additional invariant that location would uniquely enforce.

`RankingSpec` — `{ sortBy, direction, limit }`, the one named sub-structure of `ResolvedIntent` called out separately (see above) — is the value object the "clamp `limit` to the registered endpoint's documented maximum" edge case (edge-cases.md, "Schema-Valid Intent Requests a Rank/Limit Analytics Cannot Fulfill") operates on; its invariant ("`limit` must not exceed the target endpoint's documented maximum, clamped and disclosed rather than silently rejected or silently forwarded") is enforced at `QueryPlan`-validation time, not stored as a flag anywhere — the clamp itself, if it fires, is disclosed in that turn's response and is visible in the audit trail only implicitly, via `queryParameters.limit` reflecting the clamped (not the originally-requested) value.

## What Is Deliberately *Not* Modeled as a Domain Value Object: the §13.2 Response Contract

The full `{ answer, data, visualization, metadata }` envelope (source spec §13.2) is **not** modeled as a domain value object in this document — it belongs in `api-contract.yaml`, the API Design Agent's own artifact, not here. Reasoning, drawn explicitly rather than asserted:

- **It carries no invariant of its own beyond "assembled once, from already-validated pieces, for serialization."** Every fact inside it that *does* carry a domain invariant is already modeled above under its own name: the resolved intent driving it (`ResolvedIntent`), the provenance signal (`TurnProvenance`), the two audit-worthy summary facts (`FinalResponseSummary`, `groundingCheckResult`). The envelope itself is a wire-format grouping of already-modeled facts plus Analytics' own raw `data.rows`/`data.columns` — data this service is never permitted to durably re-own (ADR-0024) and therefore never appears as a modeled field on either aggregate.
- **It is never persisted, in whole or in part, beyond the HTTP response.** `ConversationSession` doesn't store it (only the intent and provenance survive to the next turn); `AuditRecord` doesn't store it either (only `finalResponseSummary`'s two scalar-ish fields survive, deliberately "not the full raw LLM payload, to bound log volume," §20). A concept nothing in this bounded context ever needs to look up, filter on, or enforce a rule against after the response is sent is a wire-format concern, not a domain concept — the same line `ddd-cqrs-standards.md` already draws between a read-model projection's DTO shape and its own governing aggregate.
- **The `visualization.type` enum** (`bar_chart`, `horizontal_bar_chart`, `line_chart`, `donut_chart`, `funnel_chart`, `single_stat`, `table_only`) is likewise a wire-format value chosen by §13.1's deterministic rule table at response-assembly time, not a stored domain fact — the one piece of it with any audit weight (which type was actually chosen, for observability against the LLM's own advisory `visualizationHint` — edge-cases.md's "non-event, confirmed" entry) is exactly what `FinalResponseSummary.visualizationType` already captures on `AuditRecord`; no separate visualization aggregate or value object is warranted for the rest of the envelope's shape.

## Domain Invariants (requirement-spec §4, restated in DDD terms)

- **Exactly two aggregate roots, and no analytics-shaped aggregate, full stop — ADR-0024.** Restated as this document's own top-line confirmation (see Boundary Summary): no `Product`, `Order`, `Revenue`, or any other aggregate duplicating another service's domain data exists, or is proposed, anywhere in this model. `ConversationSession` and `AuditRecord` are the entire aggregate inventory.
- **Neither aggregate may hold a durable copy of another bounded context's owned data.** `ConversationSession.lastTurnProvenance` and `AuditRecord.turnProvenance` hold only Analytics' *signal* (`isProvisional`/`reconciledThrough`), never its underlying figures; `AuditRecord.resultSize` is a count, never the rows; `queryParameters`/`toolsInvoked` name *which* Analytics endpoint and parameters were used, never a copy of what it returned. Every reference to another bounded context's identifiers (`userId`, `role`) is opaque, exactly the pattern every other service's `ddd-model.md` on this platform already follows for cross-context references.
- **Exactly one synchronous dependency; zero domain events, published or consumed, by either aggregate.** Unlike `kart-analytics-service` (`EventIngested`, `ReconciliationCompleted`, etc.) or `kart-delivery-tracking-service` (`CarrierStatusIngested`), neither `ConversationSession` nor `AuditRecord` has any internal or external domain event — see Modeling Decision 3 below. This is the DDD-model-level confirmation of ADR-0024's "no asynchronous publish or consume relationships" and requirement-spec §5's explicit "Published events: None / Consumed events: None."
- **The LLM never invents business data — enforced structurally, not by either aggregate's own invariant alone.** `ResolvedIntent.metric`/`.entity`/`.dimensions` values are only ever drawn from the closed metric/entity/dimension registry (§6/§7), an external, versioned application-config artifact this document deliberately does not model as a domain aggregate (design-decisions.md's Caching decision already treats it as static config, not business data with its own lifecycle) — `ResolvedIntent`'s own schema-validity is a precondition to the value object's existence, not a rule the value object enforces on itself after the fact.
- **No query executes without all three RBAC checks (Gateway → `ai-assistant.query` → `analytics.dashboards.read`) having already passed.** This is a precondition on ever reaching the point where a `QueryPlan` is built or an `AuditRecord` is created for a data-bearing turn — see Authorization below for why this is not itself a locally-owned permission aggregate.
- **"Not supported" and "supported, zero rows" are structurally distinguishable outcomes, never conflated.** Enforced at the `AuditRecord.errors` level (an `unsupported`-category `ErrorDetail` vs. no error at all with a zero-row `finalResponseSummary`) — this is the same FR-009 distinction requirement-spec §4 states, restated as a field-level rule on the one aggregate that has to make it durable and inspectable after the fact.
- **Provisional data is always surfaced, never smoothed over — enforced at the value-object level.** `TurnProvenance` is not an optional afterthought field bolted onto a response; it is a first-class value object embedded on both aggregates specifically so it can never be silently dropped between "Analytics returned it" and "the audit trail records it" (FR-012).

## Authorization Modeling: `ai-assistant.query` (ADR-0025)

**Confirmed explicitly, not left ambiguous: `ai-assistant.query` does not need, and does not get, a domain aggregate of its own.** ADR-0025's own Consequences section states this directly — "there is no `PermissionGrant`-shaped entity to design here, unlike Admin Service's `admin_permission_grants`" — and this model concurs, for the same reason Analytics' own `analytics.dashboards.read` needed none: the scope is issued Identity-side, embedded directly in the human user's JWT at token-mint time via Identity's existing role→scope mapping (both `Admin` and `Support Agent` roles resolve to include it), with **no persisted grant table anywhere**, because there is no per-user variation to persist — every `Admin`/`Support Agent` who can reach this feature at all gets the identical scope. Contrast this directly with `kart-admin-service`'s `AdminPermissionGrant` aggregate, which exists precisely *because* Admin's fine-grained permission is per-`(principalId, category)` and revocable independently of the coarse role claim — `ai-assistant.query` has no such per-principal variation to model.

Concretely: the scope check (`bearerAuth: [ai-assistant.query]`, enforced at this service's own API boundary before any `QueryPlan` is built) is a stateless, inline check against the Gateway-forwarded JWT's `scopes` claim — pure application/middleware logic, not a read against either `ConversationSession` or `AuditRecord`. The *fact* that a turn passed (or failed) this check is what an `unauthorized`-category `ErrorDetail` on `AuditRecord` records after the fact, for audit purposes — but the check itself has no aggregate to consult, unlike Admin's live, uncached `AdminPermissionGrant` lookup on every `/admin/*` request. This is the correct, closed shape per ADR-0025 and is not reopened here.

## Cross-Aggregate Interaction

A single turn touches both aggregates, but never in one transaction — they live in different stores entirely:

1. **Read `ConversationSession` (if `conversationId` supplied).** A per-`conversationId` Redis lock is acquired first (design-decisions.md's Concurrency Control decision) so no second in-flight turn for the same conversation can race this read; the existing `lastResolvedIntent`/`lastTurnProvenance` (if present and not expired) become the follow-up-merge context for FR-007's translation step.
2. **Build and execute a `QueryPlan` (transient, not persisted independently — see above), call the Model Gateway twice (plan, explain), call Analytics once (or twice, for a comparison).** None of this touches either aggregate directly; it is ordinary request-handling application logic operating on values, not aggregate state.
3. **Write `AuditRecord` (a single insert, one row, this turn's own new `TurnId`) — always, regardless of outcome.** This is the one durable, append-only fact this turn produces.
4. **Upsert `ConversationSession` (only if the turn produced a new resolved intent — i.e., not for a hard pre-translation rejection) — overwriting `lastResolvedIntent`/`lastTurnProvenance` wholesale, refreshing the sliding TTL.** Release the per-`conversationId` lock.

Steps 3 and 4 are two independent writes to two independent stores, coordinated only by the per-`conversationId` lock acquired in step 1 (which guarantees no second turn interleaves between them for the same conversation) — never a two-phase-commit or shared transaction. A crash between step 3 and step 4 leaves a durable, correct `AuditRecord` for the turn that did complete, with `ConversationSession` simply not advancing to reflect it — the next turn for that conversation would then be interpreted against the *previous* turn's intent, a stale-but-not-corrupt outcome no worse than the session having expired outright, and one the sliding-TTL/expired-session handling already tolerates by design.

`ConversationSession` never reads or references `AuditRecord`, and `AuditRecord` never reads `ConversationSession` at write time (it only stores that turn's own already-known values) — the only place the two are ever correlated is a later, out-of-band audit query joining on `conversationId` (e.g., reconstructing a conversation's full transcript by listing every `AuditRecord` for that `conversationId`, ordered by `timestamp`) — a read-time join, never a write-time coupling.

## Modeling Decisions & Assumptions (resolved here, not escalated — engineering defaults, revisable)

1. **Two aggregates, not one — transaction-boundary test applied, per ADR-0024's own mandate.** `ConversationSession` (Redis, ephemeral, single-mutable-slot, TTL-bound) and `AuditRecord` (a durable, append-only store, must outlive the session) cannot be one aggregate: they don't share a datastore, a lifecycle, or a query pattern. This is not a discretionary split — it is the only shape consistent with ADR-0024's explicit two-item ownership table and the edge-case decision that "turns outlive a session's active lifetime."
2. **`ResolvedIntent` is a value object, duplicated by value across both aggregates, never shared by reference.** See the dedicated reasoning section above — the deciding factors are "no independent lookup-by-id ever needed," "naturally replaced wholesale, not mutated," and "two aggregates need their own independent, non-interfering copies at different points in time."
3. **No internal domain events proposed for either aggregate.** Unlike `kart-analytics-service` (`EventIngested`, `ReconciliationCompleted`, ...) or `kart-delivery-tracking-service` (`CarrierStatusIngested`, `UnmappedCarrierStatusFlagged`), neither aggregate here has an asynchronous internal processing step for an event to drive — every step in a turn (translate → validate → execute → explain → persist) is a direct, synchronous, in-process sequence within one request handler, the same reasoning `kart-admin-service/ddd-model.md`'s Modeling Decision 3 already gives for its own two aggregates. A future genuinely async internal step (there is none proposed by any approved upstream document) would be the trigger to revisit this, not something anticipated here.
4. **The per-`conversationId` Redis lock (`ai-assistant:session-lock:{conversationId}`) is an infrastructure/concurrency mechanism, not a modeled domain entity.** It has no invariant of its own beyond "mutual exclusion for the duration of one turn," already fully specified at the design-decisions.md stage (`SET NX PX`) — introducing a `SessionLock` entity here would model a technical mechanism as if it were a business concept, which it isn't.
5. **`QueryPlan` and `RankingSpec` are named value objects precisely because each carries its own stated invariant (FR-002's endpoint/parameter-contract rule; the rank/limit clamping rule) — but neither is independently persisted.** See the dedicated reasoning section above. This is a deliberate middle ground: naming a concept in this document because it has a real rule attached to it, without over-modeling it as if it needed its own storage or identity.
6. **The §13.2 response contract, and the `visualization.type` enum specifically, are wire format, not domain value objects — left to `api-contract.yaml`.** See the dedicated reasoning section above; the two facts from that envelope with genuine audit weight (`finalResponseSummary`, `groundingCheckResult`) are already captured as `AuditRecord` fields per §20, so nothing is lost by not also modeling the full envelope shape here.
7. **The metric/entity/dimension/endpoint registry (§6, §7, §10.3) is referenced, never modeled as this service's own aggregate.** It is external, versioned application config (design-decisions.md's Caching decision already treats it this way) that `ResolvedIntent`'s field values are validated against — it has no per-instance identity, no write path from any request handler, and no lifecycle beyond "reviewed and deployed like any other service's API contract" (Maintainability NFR, requirement-spec §3). Modeling it as an aggregate would misrepresent static config as business data with its own invariants to enforce at runtime.
8. **Naming: `ConversationSession`, not bare "Session," to avoid a collision with `kart-identity-service`'s already-owned term.** See the dedicated naming note under the ConversationSession aggregate above and the ubiquitous-language.md update below.
