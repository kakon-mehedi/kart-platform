# Design Decisions: kart-ai-assistant-service

Cross-cutting technology/design-pattern choices this service's requirement-spec.md and edge-cases.md force. Service boundaries, aggregate/domain model, and schema/table design are explicitly left to the Architecture, DDD, and Database Design Agents that follow this stage. Several decisions here restate a fix `edge-cases.md` already chose, generalized into this service's standing pattern — cited, not re-derived.

## Decision: Model-Gateway / LLM-Provider Abstraction

- **Requirement driving this:** requirement-spec §1 "LLM-provider framing" ("this document is deliberately LLM-provider-agnostic... provider/model selection is an implementation detail for a later stage") and its API-surface entry for "Model-gateway calls" (§5); source spec §21.4 (two call shapes: structured-output "plan" call, "explain" call) and §11 (two-LLM-call architecture, D2); the platform's own non-negotiable Model Gateway pattern (`PLATFORM_BLUEPRINT.md` §8.1: "No agent ever calls a provider SDK directly").
- **Options considered (3):** This service calls a named vendor SDK (e.g., Anthropic's client) directly, with provider selection as an internal `if`/config branch · This service depends on the platform's `ModelGateway`/`ModelProvider` interface (`complete()`, `supportsTools()`, `supportsStructuredOutput()`, `contextWindow()`) and requests a model **tier**, never a vendor, per `models.yaml`/`routing.yaml` (`PLATFORM_BLUEPRINT.md` §8.1) · This service defines its own bespoke provider-abstraction interface, independent of the platform's existing Model Gateway
- **Decision:**
  - Chosen: the second option — `kart-ai-assistant-service` depends only on the platform's existing `ModelProvider`-shaped interface, and issues two distinct **tier requests**, not vendor requests, one per call shape: a `structured-output`-capable tier for the plan call (§8's intent JSON schema, §12's bounded tool-calling registry — requires `supportsStructuredOutput`/`supportsTools`) and a cheaper/faster tier for the explain call (free-text generation grounded in already-fetched data, no tool-calling needed). The adapter layer normalizes structured-output enforcement so the plan call's JSON-schema contract holds regardless of which underlying provider is configured for that tier.
  - Why: requirement-spec §1 already forbids naming a vendor anywhere in this service's own docs — depending on a bespoke, service-local abstraction (option 3) would just re-invent what the platform already guarantees platform-wide (`PLATFORM_BLUEPRINT.md` §8.1: "swapping the underlying LLM... is a one-line change in `routing.yaml`. No agent code changes, no prompt changes"), and calling a vendor SDK directly (option 1) is exactly what §1/§21.4 rule out. Reusing the existing interface also means this service's two call shapes map cleanly onto the interface's existing capability flags instead of inventing a second, parallel notion of "capability" specific to this service.
  - Trade-off accepted: this service is bound to whatever capability flags/tiers the platform's Model Gateway already exposes — if a future call shape needs a capability the interface doesn't yet flag (e.g., a third call type), that is a Model Gateway extension request to the platform layer, not something this service can patch around locally.

## Decision: Conversation-Session Storage

- **Requirement driving this:** requirement-spec §4 Domain Invariant #1 / §14.1 of the source spec ("the last resolved structured intent per session" is the authoritative state a follow-up merges against — session/raw-transcript is *not* the authoritative state); requirement-spec §3 Scalability NFR ("stateless orchestrator, horizontally scalable"); UX-1 (session TTL/idle timeout — genuinely open, requirement-spec §8, not resolved here); edge-cases.md's "Conversation Session Expiry Mid-Conversation" (sliding-window idle timer) and "Follow-up Against Data That Has Since Changed" (session state additionally carries prior-turn provenance metadata for comparison).
- **Options considered (4):** In-memory (process-local) session store · A small dedicated PostgreSQL table (`conversation_session`, keyed by `conversationId`, with an expiry column and a cleanup job) · MongoDB collection · Redis, namespaced (`ai-assistant:session:{conversationId}`), reusing the platform's existing Redis deployment
- **Decision:**
  - Chosen: Redis, key-namespaced per the platform's existing convention (`identity-service`'s `identity:revocation:*`/`identity:mfa-challenge:*` pattern, `PLATFORM_BLUEPRINT.md` §15's Redis row: "cache-aside for reads... key convention `service:entity:id[:shard]`") — `ai-assistant:session:{conversationId}` holding the last resolved structured intent (§8) plus the small addition of prior-turn `isProvisional`/`reconciledThrough` provenance the "stale cross-turn context" edge case requires. TTL/idle-expiry is implemented via Redis's native key expiry with sliding refresh on every turn (matching the edge case's "sliding-window idle timer" decision); the concrete duration is UX-1, still an open human decision — this design only fixes the mechanism, not the number.
  - Why: In-memory is rejected outright by the Scalability NFR itself — a horizontally scaled, stateless orchestrator cannot pin a conversation to one instance's process memory, and a restart would silently lose every active session's context (an orphaned-follow-up failure mode the expiry edge case already treats as something to actively avoid, not induce by accident). A dedicated Postgres table is rejected because this data has no relational shape and no durability requirement beyond the session's own idle window — ADR-0024's ownership table is explicit that conversation/session state is "eventually-irrelevant local state," not business data warranting Postgres's durability/transactional guarantees, and a TTL in Postgres means a cleanup job component this data doesn't need. MongoDB is rejected for the same reason: this is a small, single-document, pure key-value read/write per turn — no query flexibility, aggregation, or large-document use case Mongo is suited for — and Mongo has no first-class key-expiry primitive as cheap as Redis's `EXPIRE`. Redis is already the platform's standing choice for exactly this profile (ephemeral, TTL-bound, per-key state with no cross-key relational structure) at both `kart-cart-service` (cart state, TTL-bound) and `kart-identity-service` (ephemeral security state) — reusing it here is consistent, not a new infrastructure dependency for the platform.
  - Trade-off accepted: this service's request path now has a hard runtime dependency on Redis availability for every follow-up turn (a fresh, no-`conversationId` turn is unaffected) — the same trade-off `kart-identity-service`'s design-decisions.md already accepts for its own Redis-backed ephemeral state, mitigated by the resilience pattern below, not eliminated. A Redis outage degrades follow-up interpretation (forces every turn to be treated as fresh, or to surface the same "expired session" error the TTL case already defines) but never blocks a fresh, context-free question, since Redis is not on the path to Analytics or the LLM.

## Decision: Resilience Pattern for LLM-Provider and Analytics Outages

- **Requirement driving this:** edge-cases.md's "LLM Provider Unavailable/Timeout — Plan Call vs. Explain Call" (differentiated handling, bounded single retry, failure point recorded in audit) and "`kart-analytics-service` Unavailable/Timeout" (circuit breaker + bounded timeout/retry, fail closed, no caching/no LLM improvisation) — both already resolved at the edge-case stage; this generalizes them into the service's one standing resilience-pattern decision. Ties to the platform's existing per-downstream resilience vocabulary already named in `kart-admin-service/design-decisions.md` ("a short per-call timeout carved out of the... write budget, a small bounded retry... and independent circuit breakers... one per owning service — rather than one shared breaker") and reused by this service's own edge-cases.md for the Analytics-outage decision.
- **Options considered (3):** Timeout + bounded single retry only, no circuit breaker, on every outbound call · Independent circuit breaker per call-site (plan-call, explain-call, Analytics-call) + a timeout budget + one bounded retry before the breaker/fallback fires (the option both governing edge cases already chose) · Bulkhead (separate connection/thread pool per dependency) with no circuit breaker
- **Decision:**
  - Chosen: three independent circuit breakers — one for the plan call, one for the explain call, one for the Analytics call — each with its own timeout budget and a single bounded retry before falling into that call-site's own already-specified fallback (plan-call failure → generic "assistant unavailable"; explain-call failure → FR-004's template-built answer from already-fetched data; Analytics-call failure → the "data source unavailable" error type, §19/§21.1). Retry budget is exactly one, not unbounded, matching `kart-admin-service`'s "short timeout + bounded retry per outbound dependency" convention that this service's own edge-cases.md already cites by name.
  - Why: independent breakers (not one shared breaker across all three call-sites) keep blast radius narrow exactly the way `kart-admin-service`'s own reasoning already establishes ("a single slow or down dependency must not silently... cascade into unrelated categories") — an open explain-call breaker must not also degrade the plan call, and an Analytics outage must not be conflated with an LLM outage in the audit record's `errors` field, since a business user (and an on-call engineer) needs to tell the two apart. Reusing this exact vocabulary/mechanism, rather than inventing a new resilience term for this service, keeps the platform's resilience-pattern catalogue to one shared mental model across `kart-admin-service`, `kart-analytics-service`, and this service.
  - Trade-off accepted: the concrete timeout budget cannot be set numerically here — it is explicitly carved "from the still-open latency budget" per edge-cases.md, and Infrastructure-1 (requirement-spec §8) leaves that budget an open human decision; this decision fixes the *mechanism* (breaker + bounded retry) and its allocation across three independent call-sites, not the number, consistent with this pipeline stage's own convention of not inventing NFR figures no source document states.

## Decision: Caching

- **Requirement driving this:** ADR-0024's data-ownership table ("A cache or local recomputation of a number Analytics itself already returns" is explicitly listed under "It may never own"); FR-003 ("This service never caches or locally recomputes what Analytics itself returns... Analytics remains the single source of truth"); requirement-spec §3 Maintainability NFR ("The metric/endpoint registry... is versioned application config, reviewed the same way any other service's API contract is reviewed").
- **Options considered (3):** No caching anywhere in this service, full stop (the most literal reading of ADR-0024) · Cache the metric/endpoint registry (§6/§7/§10.3) and the Model Gateway's tier→provider routing config in-process (loaded at startup, refreshed on deploy), while never caching any Analytics query result or LLM-generated content (the option chosen) · Cache-aside Analytics query results keyed by resolved query plan (endpoint + parameters), with a short TTL, to reduce redundant Analytics calls for repeated questions
- **Decision:**
  - Chosen: the registry (metrics, dimensions, endpoint-mapping table, per-endpoint documented parameter bounds — the "clamp to documented maximum" edge case's own config surface) and the Model Gateway's tier-routing config are cached in-process as static application config; **no query result, no fetched Analytics payload, no LLM-generated explanation, and no derived/computed figure (AOV, period-over-period %) is ever cached or persisted beyond the single turn that produced it**, other than the last resolved *intent* (not result) held in the session-storage decision above.
  - Why: ADR-0024's ban is scoped precisely — "never caches or locally recomputes **what Analytics itself returns**" — i.e., business data Analytics owns. The registry is not Analytics' data; it is this service's own versioned config describing which capabilities exist, already treated by the Maintainability NFR as "reviewed the same way any other service's API contract is reviewed" (i.e., changed by a deploy/code-review, not by a live query). Caching a thing that only changes at deploy time is an ordinary performance optimization, not a violation of "never a second owner of Analytics' data" — conflating the two would make the registry an un-cacheable value for no reason the invariant actually states. Option 3 (caching query results) is squarely what FR-003/ADR-0024 forbid — the edge case "Follow-up Against Data That Has Since Changed" is explicit that every turn, including follow-ups against an unchanged `dateRange`, must re-execute live against Analytics specifically so reconciliation-driven changes are never silently hidden behind a stale cached value.
  - Trade-off accepted: a registry change (a new metric, a new endpoint, a raised parameter bound) requires a deploy (or an explicit cache-invalidation signal) to take effect rather than being live-editable — accepted because the registry is already reviewed like a contract, not expected to change without a deploy in the first place (Maintainability NFR). This also means every query answer costs one live Analytics round-trip even for an identical, recently-asked question — accepted as the direct, non-negotiable cost of ADR-0024's ownership boundary, not something this service is free to optimize around.

## Decision: Communication Style

- **Requirement driving this:** ADR-0024 ("exactly one synchronous downstream dependency... no asynchronous publish or consume relationships"); requirement-spec §5 API Surface table ("Published events: **None**"; "Consumed events: **None**" — "stated explicitly... not left silently blank"); source spec §21.3 ("zero synchronous coupling... to Order/Product/Inventory/User services").
- **Options considered (3):** Sync-only for every external interaction (Model Gateway calls, the Analytics call) and zero event-bus participation of any kind, inbound or outbound (the option ADR-0024 already closes) · Sync for the Model Gateway/Analytics calls, plus publishing each turn's `AuditRecord` as an async platform event for a downstream compliance/BI consumer · Sync for the Analytics call, but an async fire-and-forget notification (e.g., "your report is ready") for long-running turns
- **Decision:**
  - Chosen: sync-only, exactly as ADR-0024 closes it — the plan call, the explain call, and the Analytics call are all synchronous request/response; the audit record (FR-011) is written directly to this service's own local append-only store, never published as a platform event.
  - Why: this is already a closed architectural decision (ADR-0024), not re-litigated here; restating it as this service's communication-style decision keeps this doc's catalogue complete (every service's design-decisions.md states its communication style explicitly) without reopening a question the requirement-spec's own §5 and §6 already treat as settled. The "publish the audit log as an event" option is exactly the kind of second dependency edge ADR-0024 flags as "a scope change requiring its own ADR, not an incremental addition this spec's own authority covers."
  - Trade-off accepted: no async decoupling means a slow (not yet failed) Analytics or LLM call is fully absorbed as this service's own request latency, bounded only by the resilience pattern above rather than shed onto a queue; and there is currently no way for another service to consume this service's audit trail except by directly querying whatever store holds it (mirroring how `kart-admin-service`'s `AdminActionPerformed` audit trail is itself queried, per FR-011) — a future cross-service audit-consumption need is a new integration decision, not something this doc pre-builds for.

## Decision: Concurrency Control for Session State

- **Requirement driving this:** edge-cases.md's "Concurrent Requests in the Same Conversation Session (Race on Session State)" — already resolved at the edge-case stage (serialize per `conversationId`, reject the losing concurrent request with an explicit message); requirement-spec §3 NFR ("a handful to low hundreds of concurrent users," a low-volume internal tool).
- **Options considered (3, as already framed in edge-cases.md):** No concurrency control (accept occasional last-write-wins lost updates) · Optimistic concurrency (a version/turn-sequence number on session state, rejecting a stale write) · Serialize all turns within one `conversationId` (a lightweight per-session lock/queue) — the option chosen
- **Decision:**
  - Chosen: per-`conversationId` serialization, implemented as a short-lived Redis lock (`SET NX PX`, key `ai-assistant:session-lock:{conversationId}`) taken for the duration of one turn's plan→execute→explain→persist sequence, reusing the same Redis deployment already chosen for session storage rather than standing up a second coordination store. A second request against a session already holding the lock is rejected immediately with a "a previous message in this conversation is still being processed" response, never queued or silently merged.
  - Why: already decided in edge-cases.md; restated here as the service's standing concurrency-control pattern because it generalizes past that one edge case — it is also what makes the Idempotency decision below sufficient without a separate mechanism. Optimistic concurrency (a version/turn-sequence field) was rejected in edge-cases.md because a genuine race could still silently merge a follow-up against the wrong prior intent with no way for the user to detect it, which would violate FR-007's "every field not addressed carries forward unchanged" guarantee; this service's own low concurrency profile (§3 NFR) makes the stricter serialize-and-reject option cheap rather than a throughput risk.
  - Trade-off accepted: a legitimate double-submit (e.g., a flaky UI retry) surfaces as an explicit rejection rather than silent deduplication — already accepted in edge-cases.md, restated here since it is this same trade-off that lets the Idempotency decision below avoid a second, dedicated mechanism.

## Decision: Idempotency

- **Requirement driving this:** requirement-spec §1 ("Read-only, full stop... never mutates any business data anywhere on the platform") — this service has no money-moving or business-data-mutating endpoint at all, unlike `kart-admin-service`'s outbound writes to owning services; but `POST /v1/ai-assistant/query` is not side-effect-free either, since it writes this service's own two local aggregates (session state, one audit record per turn, FR-011) on every call.
- **Options considered (3):** No idempotency mechanism of any kind — treat every POST as a fresh turn (risk: a client-retried request could produce two audit records for one logical turn, or a corrupted double-merge against session state) · A formal `Idempotency-Key` header + server-side dedupe table, mirroring the platform's `api-standards.md` convention ("mandatory on every... non-retry-safe write") that `kart-admin-service` adopts for its own outbound business-mutating calls · Rely on the per-`conversationId` serialization already decided above to reject a concurrent duplicate outright, with no separate formal idempotency-key mechanism
- **Decision:**
  - Chosen: the third option — no dedicated `Idempotency-Key` mechanism. The per-`conversationId` serialization (previous decision) already rejects a concurrent duplicate request before it can produce a second audit record or a corrupted session-state merge, which is the specific failure mode a formal idempotency key would otherwise exist to prevent.
  - Why: the NFR category this decision covers — "does a retried/duplicated request produce an unsafe duplicate effect" — is a real question for `kart-admin-service` because its retries flow through to *another service's* write API (double-issuing a coupon, double-locking a user is a high-impact, cross-service effect); this service's only "mutation" is its own two local, non-business aggregates, and the concurrency-control decision above already closes the one path (a genuine in-flight race) that could turn a duplicate request into a duplicate effect. A formal idempotency key would duplicate a guarantee this service already has for free from a decision made for an unrelated reason (correctness of follow-up merging, not retry-safety). This mirrors how a read-only service on this platform (`kart-search-service/design-decisions.md`) carries no idempotency-key entry at all — the category doesn't force a decision beyond what its own concurrency/consistency choices already give.
  - Trade-off accepted: a sequential retry (not concurrent — e.g., a client that waits for the first request to fully fail before retrying) is not deduplicated and will be processed as a second, independent turn, producing a second audit record — accepted because this is indistinguishable from the user legitimately asking the same question twice, and this service has no way (nor a stated need) to tell those apart without a client-supplied correlation id the spec never requires.

## Decision: Observability & Instrumentation

**Decision:** Serilog (structured logging) + OpenTelemetry SDK (distributed tracing + metrics), per the platform's reusable `observability-standards.md` and this repo's `kart-conventions.md` Observability section. Logs export via OTLP → Grafana Loki; traces via OTLP → Grafana Tempo; metrics scraped by Prometheus from `/metrics`; Grafana provides dashboards and alerting. Wired once via the shared `Kart.Shared.Observability` package, not reimplemented per service.

**Options considered:**
- Ad-hoc per-service logging/APM tool choice — rejected: fragments dashboards/alerting across the platform's services and breaks single-trace-id correlation.
- Platform-standard Serilog + OpenTelemetry + Grafana LGTM stack — adopted: one mental model and one Grafana pane regardless of which service is being inspected.

**Why:** this service's primary correlation field is `conversationId` (paired with a per-turn `turnId`), since that is what both Redis session-state keys and audit records key on. Distributed traces run the platform's standard (not 100%) sampling tier — this is not one of the platform's named 100%-trace-coverage saga services (requirement-spec §3) — but audit logging is a distinct, additional 100% requirement layered on top of standard-tier tracing, per FR-011/requirement-spec §3 Observability row: every turn (successful, clarification, or error) produces exactly one structured audit record regardless of trace-sampling decisions, since the audit trail is a business/compliance requirement, not a diagnostic one. The two concrete signals worth a dashboard panel, tying directly to the Resilience Pattern decision above: per-call-site circuit-breaker state (plan/explain/Analytics, so an open breaker is visible before it's inferred from a spike in fallback responses) and the plan-vs-explain failure split already recorded in each audit record's `errors` field.

## Decision: Global Exception Handling & Consistent Response Model

**Decision:** A single global exception-handling middleware (ASP.NET Core `IExceptionHandler`/`UseExceptionHandler`) is the only place this service catches and translates unhandled exceptions into an HTTP response — no handler/controller/domain code wraps business logic in try/catch purely to log-and-rethrow or log-and-return an error. Every error response (validation failure or unhandled exception) is shaped as an RFC 7807 `ProblemDetails` envelope extended with the platform's standard fields (`traceId`, `errorCode`); every success response follows the same consistent envelope convention as every other Kart service. Both the middleware and the `ProblemDetails` factory are wired once via the shared `Kart.Shared.ErrorHandling` package, not reimplemented locally.

**Options considered:**
- Per-handler/controller try/catch translating exceptions to a response inline — rejected: duplicates translation logic per endpoint and risks an inconsistent shape between this service's five *domain* error types (unsupported/ambiguous/unauthorized/unavailable/no-data, §19/§21.1) and a genuinely unhandled infrastructure fault.
- Platform-standard global exception handler + `Kart.Shared.ErrorHandling`-wired `ProblemDetails` envelope — adopted: one place to change the error shape platform-wide, consistent with every other Kart service `kart-admin-web` already talks to.

**Why:** this service's five named error `type` values (§19/§21.1: unsupported, ambiguous, unauthorized, unavailable, no-data) are domain/business outcomes returned via the platform's Result/Either pattern (`api-standards.md`), never raised as exceptions — a clarification or an "unsupported capability" response is an expected, first-class outcome (FR-008/FR-009), not an error condition to be caught. The global exception handler exists only for the genuinely exceptional case (e.g., an unhandled fault in the Model Gateway adapter or Analytics client that escapes the circuit breaker's own typed failure path), logging it exactly once at `Error` level tagged with `traceId`/`conversationId`/`turnId` through the same Serilog/OTel pipeline named above, never a second, ad-hoc log line from a local catch block.
