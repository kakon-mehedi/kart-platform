# Requirement Spec: kart-ai-assistant-service

## 1. Scope

Covers a single, brand-new capability: the **Kart Business Assistant**, a natural-language, business-facing Generative AI assistant surfaced inside `kart-admin-web` and backed by a new service, `kart-ai-assistant-service`. Unlike every other `requirement-spec.md` in this repo, the primary source is not a BRD excerpt but a dedicated, already-detailed specification document — `docs/requirements/genai-business-assistant-spec.md` — that itself cites the BRD (`kart-requirements.md`), the 18-flow catalog (`business-flows.md`, Flow 18), and `kart-analytics-service`'s own approved docs. This spec restates that document's requirements in this repo's requirement-spec voice/format and folds in four ADRs that have since closed decisions the source spec had left as open questions.

**Bounded-context status — closed, not re-litigated here (ADR-0024):** `kart-ai-assistant-service` is a new, independently deployed bounded context — the platform's 19th deployable repo, following the existing one-bounded-context-per-repo convention (`docs/architecture/container-diagram.md`). It is not a module inside `kart-admin-service` or a synchronous extension of `kart-analytics-service`; that placement question is closed, per ADR-0024, and is not reopened by this document.

**Scope boundary (closed, ADR-0024):**
- **Read-only, full stop.** This service never mutates any business data anywhere on the platform (source spec §1.5, §9, §16, NG8). It owns no `Product`, `Order`, `Revenue`, or other domain aggregate belonging to another service.
- **Exactly one synchronous downstream dependency:** `kart-analytics-service`'s internal query API (existing ten dashboards/funnels + one new product-performance endpoint, §10.3 of the source spec). No direct calls to `kart-order-service`, `kart-product-service`, `kart-inventory-service`, or `kart-user-service`.
- **No asynchronous publish or consume relationships.** This service publishes nothing to the event bus and consumes nothing from it — stated explicitly here, per the precedent `kart-admin-service/event-contract.md` and `kart-identity-service/requirement-spec.md` already set for purely-synchronous services, rather than left silently blank.
- **Data ownership is limited to two things it may hold locally:** conversation/session state (the last resolved structured intent per session) and its own append-only audit log. It may never hold a copy of Analytics' dashboard/read-model data, or any copy of Order/Product/Inventory/User domain data — the same "never a second owner of another service's domain data" invariant ADR-0024 applies by direct analogy to `kart-admin-service`'s own Domain Invariant #3.

**RBAC/scope boundary (closed, ADR-0025):** access is gated by a new scope, `ai-assistant.query`, Identity-issued via role→scope mapping into the human user's own JWT for both the `Admin` and `Support Agent` roles (not a persisted grant table — there is no per-user variation to persist, the same reasoning already applied to Analytics' own `analytics.dashboards.read`). It is enforced via the `bearerAuth` OpenAPI security scheme (human-JWT shape, matching `kart-admin-service`'s convention, not Analytics' `internalClientCredentials` shape), on the same Gateway-forwarded, unmodified JWT (ADR-0023). See §4 and §7 below.

**Explicitly out of scope, permanently, not "TBD":**
- **Seller/Vendor performance reporting** — ruled permanently out of scope by **ADR-0026**: no Seller/Vendor bounded context, aggregate, or field exists anywhere in the platform's 18-service architecture; `business-flows.md`'s Flow 16/18 references to it are aspirational business-flows scope, not implemented architecture. No extensibility hook for a future Seller dimension is to be built into this service's registry, intent schema, or endpoint-mapping table (ADR-0026, Decision 3).
- **Geographic/location analytics** ("top area," "sales in Dhaka") — ruled permanently out of scope for this build by **ADR-0027**: this is *not* a cheap future read-model addition, contrary to the source spec's own framing of it as a possible "moderate-effort" gap (§26-Data-1). ADR-0027's finding is that `kart-order-service`'s `OrderConfirmed.address` field has no confirmed shape in that service's own approved contract at all (no `Address`/`AddressDetail` value object, no Postgres column, no OpenAPI schema) — geographic analytics requires a `kart-order-service` producer-side event-contract change first, a cross-team prerequisite outside this service's own roadmap. This document cites ADR-0027, not merely the source spec's §26-Data-1, as the authority for this exclusion.

**LLM-provider framing (source spec §21.4, carried forward unchanged):** this document is deliberately LLM-provider-agnostic. Every requirement below is expressed against a model-gateway abstraction and a closed structured-output/tool-calling contract, never a named vendor or model. Provider/model selection is an implementation detail for a later stage, not a requirement this spec states or blocks on (source spec §26-AI-1).

## 2. Functional Requirements

Restated from the source spec's FR-001–FR-012 (`genai-business-assistant-spec.md` §4), service-scoped and in this repo's requirement-spec voice rather than copied verbatim.

- **Question intake.** Accept a free-text business question (UTF-8, ≤ 1,000 characters) from an authenticated `Admin`/`Support Agent` caller, together with the caller's JWT and a conversation session id; route it to NL→intent translation with the prior turn's resolved intent (if any) as context. An unauthorized caller is rejected (403) before the LLM is ever invoked — the scope check (§4, ADR-0025) always runs first, saving cost and closing off any downstream bypass path (source FR-001).
- **Intent-to-query translation.** Deterministic application code — never the LLM — maps the structured intent (§8 of the source spec) onto exactly one call against `kart-analytics-service`'s registered query surface (the ten existing dashboards/funnels plus the one new product-performance capability, source spec §10.3). An intent with no matching registered capability returns an explicit "unsupported" result, never a best-effort guess (source FR-002).
- **Query execution against trusted data.** Execute the resolved query plan against `kart-analytics-service` over OAuth2 Client Credentials carrying the existing `analytics.dashboards.read` scope; pass the raw result — including its `isProvisional`/`reconciledThrough` fields — forward unmodified. This service never caches or locally recomputes a number Analytics itself already owns (source FR-003; the ownership boundary this enforces is formalized platform-wide by ADR-0024).
- **Result-grounded explanation generation.** Generate the natural-language answer strictly from the already-fetched result; a post-generation validation step checks that every numeric token in the generated text traces to a value in the result payload. On a grounding-check failure, discard the generated text and substitute a template-built answer assembled directly from the data, and log the failure (source FR-004).
- **Table rendering.** Every successful answer includes the structured data behind it as a table, whether or not a chart is also shown — a table is never omitted in favor of a chart alone (source FR-005).
- **Visualization selection.** Choose a chart type (or none) by the deterministic rule table in the source spec (§13), not by open-ended LLM discretion; the LLM may propose an advisory `visualizationHint`, which the application is free to override, except when the user's own words explicitly request a specific chart type (source FR-006).
- **Conversational follow-up handling.** Interpret a follow-up message as a modification of the previous turn's resolved structured intent — every field the new message doesn't address carries forward unchanged. A follow-up that clearly starts a new topic resets context instead of forcing an incoherent merge, and this reset is itself logged for observability (source FR-007).
- **Ambiguity detection & clarification.** When a question's metric, entity, or time range cannot be resolved to exactly one supported definition, return a clarifying question with concrete, selectable options instead of guessing — the canonical trigger is a ranking/superlative term ("best," "top," "worst") used with no metric named and no prior-turn context to inherit one from (source FR-008).
- **Insufficient/unsupported data handling.** Distinguish, as two different response types, "there is no such data" (an out-of-scope dimension — Geography per ADR-0027, Seller/Vendor per ADR-0026) from "there is a valid query, it returned zero rows." The former must name plainly what is missing, never return a fabricated or empty-looking success (source FR-009).
- **Authorization enforcement.** Enforce the platform's three-check RBAC model on every request: (1) Gateway coarse-role check (`Admin`/`Support Agent` only), (2) this service's own `ai-assistant.query` scope check (ADR-0025), (3) `kart-analytics-service`'s own `analytics.dashboards.read` scope check on the downstream call. Failure returns 401/403 at the earliest check that fails; a `Customer`-role (or unauthenticated) caller never reaches this service, the LLM, or Analytics at all (source FR-010).
- **Audit logging of every turn.** Persist exactly one structured, append-only audit record per turn (successful, clarification, or error) — question, resolved intent, query executed, data source, response — queryable the same way `kart-admin-service`'s `AdminActionPerformed` audit trail already is. No raw LLM provider request/response body containing customer PII is retained beyond what debugging needs; the log is analytics-metadata-only in the common case (source FR-011).
- **Provisional-data disclosure.** Whenever the underlying `DashboardEnvelope` carries `isProvisional`/`reconciledThrough`, surface both explicitly in the answer text and in the response's `metadata` — never omit this signal to make an answer look more finished than the underlying data actually is (source FR-012).

## 4. Domain Invariants

- **This service owns exactly two local aggregates and nothing else — closed by ADR-0024, direct analogy to `kart-admin-service`'s Domain Invariant #3.** It may own conversation/session state (the last resolved structured intent per session, source spec §14) and its own audit record (one per turn, source spec §20). It may never own, cache, or locally recompute a copy of Analytics' dashboard/read-model data (revenue, orders, product performance, etc.), nor any copy of Order/Product/Inventory/User domain data. A future DDD pass must not introduce a `Product`, `Order`, `Revenue`, or any other aggregate that duplicates another service's domain data.
- **Exactly one synchronous dependency, no async edges — closed by ADR-0024.** This service calls only `kart-analytics-service`'s internal query API; it never calls Order/Product/Inventory/User services directly, and it publishes and consumes zero platform events. Any future proposal to add a second downstream dependency or an event edge is a scope change requiring its own ADR, not an incremental addition this spec's own authority covers.
- **The LLM never invents business data.** It never states a number, product name, or category that did not come from a query result already fetched by application code in the same turn (source spec §9, §16). Numeric grounding is enforced mechanically (FR-004), not by prompt instruction alone.
- **Every metric name resolves to exactly one closed-registry definition.** The LLM selects among the metric/entity/dimension definitions in the source spec's §6/§7 — it never invents its own interpretation of a business term, and structured-output/function-calling constraints make it structurally unable to emit an unregistered metric, entity, or endpoint (source spec §8, §12, §16).
- **No query executes without passing all three RBAC checks in order.** Gateway coarse-role check → this service's own `ai-assistant.query` scope check (ADR-0025) → Analytics' own `analytics.dashboards.read` scope check on the downstream call. There is no path by which a caller reaches Analytics' data without satisfying all three, and no new bypass path is introduced by this service being a new caller of Analytics' existing security model (source spec §17, FR-010).
- **A "not currently supported" response is never conflated with a "supported, zero results" response.** These are structurally distinguishable response types (source spec §19, FR-009) so that a business user can always tell "there is no such data" apart from "there is a query, it just returned zero" — this distinction is load-bearing for the Seller/Vendor (ADR-0026) and Geography (ADR-0027) exclusions, both of which must always resolve to the former, never a fabricated or empty-looking success.
- **Provisional data is always surfaced, never smoothed over.** Whenever `isProvisional`/`reconciledThrough` is present on a fetched result, it must appear in both the answer text and the response metadata (FR-012) — the same "surface, don't hide" convention Analytics itself already follows.

## 6. Out of Scope — Closed Rulings

These are not open questions; they are decisions already closed by ADR and are not reopened by this document.

- **Seller/Vendor performance reporting — permanently out of scope (ADR-0026).** `business-flows.md` Flow 16/18 names Seller/Vendor onboarding and performance reporting, but no Seller/Vendor bounded context, aggregate, or field exists anywhere in the platform's actual 18-service architecture. This is ruled aspirational business-flows scope, not an implementation gap this capability must backfill. No placeholder field, dimension, or extensibility hook for a future Seller/Vendor capability is to be reserved in this service's registry, intent schema, or endpoint-mapping table (ADR-0026, Decision 3). If a real Seller/Vendor service is ever built, exposing its data through the assistant is a normal, incremental registry addition at that time, following the same precedent the product-performance read model already sets — not something designed for now.
- **Geographic/location analytics — permanently out of scope for this build (ADR-0027).** Not a cheap future read-model addition: `kart-order-service`'s `OrderConfirmed.address` field has no confirmed shape anywhere in that service's own approved contract (`event-contract.md` lists it as a bare, untyped key; `api-contract.yaml` has zero occurrences of `address`; `ddd-model.md`'s `Order` aggregate has no `Address` value object; `database-design.md` states explicitly no address data is persisted on any Order table). Geographic analytics is gated on a `kart-order-service` producer-side event-contract change — a cross-team prerequisite this service's own roadmap does not control. This document cites ADR-0027, not merely the source spec's own §26-Data-1, as the authority for this exclusion; no partial/best-effort attempt to derive city/region from the current undocumented `address` payload is permitted.
- **Every other Non-Goal the source spec states (§2.2) is carried forward unchanged and is not restated as an open question:** no free-form query generation against any datastore (NG1); no live/real-time operational queries against a service's own write-side database (NG4 — a live-stock question is redirected to the existing Inventory Dashboard, not answered here); no predictive/forecasting analytics (NG5); no general-purpose BI product, export engine, or "feed to external BI tools" pipeline (NG6); no multi-tenant data isolation, since Kart is single-tenant (NG7); no write-back to any business system via the assistant (NG8, reinforced by §1's read-only scope boundary above).

## 7. Resolved Decisions (ADR Citations)

Every decision below was an explicit **OPEN QUESTION** in the source spec (`genai-business-assistant-spec.md` §26) and has since been closed by ADR. This requirement-spec treats each as settled and does not re-litigate it.

1. **Bounded-context placement and data ownership — closed by ADR-0024.** Resolves source spec §26-Architecture-1 ("independent deployable vs. a module inside an existing service, extracted later"). Decision: `kart-ai-assistant-service` is a new, independently deployed bounded context (the 19th deployable repo), owning only conversation/session state and its own audit log, with exactly one synchronous dependency (`kart-analytics-service`) and zero asynchronous publish/consume relationships. See §1, §4, §5 above.
2. **RBAC scope name and issuance mechanism — closed by ADR-0025.** Resolves source spec §26-Security-1 ("exact mechanism and name for the new `ai-assistant.query`-equivalent scope"). Decision: the scope is named `ai-assistant.query` (a 2-segment `<service>.<action>` shape, not a 3-segment `<service>.<resource>.<verb>` shape, since this service exposes exactly one action), Identity-issued via role→scope mapping into the JWT `scopes` claim for both `Admin` and `Support Agent` roles (no persisted grant table), and enforced via the `bearerAuth` OpenAPI security scheme on the human-user JWT forwarded unchanged by the Gateway (ADR-0023). See §1, §4, §5 above.
3. **Seller/Vendor reporting gap — closed by ADR-0026.** Resolves source spec §26-Data-2 and §26-Business-2 (whether `business-flows.md` Flow 16/18's Seller references are a real domain gap to build toward, and whether this service's registry should reserve extensibility for it). Decision: aspirational business-flows scope, not implemented architecture; permanently out of scope; no extensibility hook reserved. See §6 above.
4. **Geographic analytics cost/feasibility — closed by ADR-0027.** Resolves source spec §26-Data-1 (whether `OrderConfirmed.address` is a structured object or an opaque string, and therefore whether geographic analytics is a cheap read-model addition or a contract-change prerequisite). Decision: the field has no confirmed shape at all in `kart-order-service`'s own approved contract; geographic analytics requires a producer-side event-contract change first, not a same-team Analytics read-model addition. See §6 above.

## 8. Open Questions / Flagged Ambiguities

These remain genuinely open — no ADR has closed them, and this pipeline stage does not resolve them by picking a default. Each is a human-approval gate per this agent's own escalation rule.

- **Business-1 — Gross vs. net revenue (inherited from Analytics, not this service's own call).** The source spec adopts gross revenue (all `PaymentCompleted` totals, before subsequent refunds) as an explicit **ASSUMPTION**, pending confirmation from whoever owns `kart-analytics-service`'s business definitions (`genai-business-assistant-spec.md` §6, §26-Business-1). This is Analytics' own metric definition, not something `kart-ai-assistant-service` defines or can resolve unilaterally — this service only surfaces whatever `revenue_dashboard.revenue` already means. Flagged here because it materially affects whether this assistant's "Revenue" answers are usable for financial reporting versus operational/directional reporting only, and must be confirmed before Revenue is treated as authoritative for financial reporting.
- **UX-1 — Conversation session TTL/idle timeout.** No concrete figure is specified anywhere in the source docs for how long a conversation's resolved-intent context should persist before expiring (`genai-business-assistant-spec.md` §14.3, §26-UX-1). The source spec's own recommendation — match `kart-admin-web`'s own session idle timeout (15/20-minute idle caps for Admin/Support Agent, per `kart-admin-web/architecture.md`) — is carried forward here as the working recommendation, **not adopted as a decided value**: it still needs explicit confirmation from whoever owns `kart-admin-web`'s session-timeout configuration before it is treated as this service's own binding TTL.
- **UX-2 — Default date range when a question names no explicit time window.** E.g., "what were the peak sales hours?" with no "last N days" stated (`genai-business-assistant-spec.md` §23 Example 5, §26-UX-2). The source spec's own examples assume "last 7 days" as a working default, but this is explicitly not a decided value — the concrete default (and whether it should be user-configurable) needs a product decision before this behavior ships.
- **Infrastructure-1 (split into two distinct budgets, carried forward as stated in §3 above):**
  - **Latency SLA** for the end-to-end turn (intake → response) — no BRD or ADR figure exists for a GenAI-inclusive round-trip; this document does not invent one (`genai-business-assistant-spec.md` §18, §26-Infrastructure-1).
  - **Cost budget/ceiling** for LLM token usage, per-turn and/or aggregate — no source document states one; this document does not invent one either (`genai-business-assistant-spec.md` §18, §26-NFR-2).
  Both require a human-set number before Phase 7 (production hardening) of the source spec's own roadmap is considered complete; neither blocks earlier implementation phases, but both must be resolved before this capability is signed off as production-ready.

**Non-blocking, carried forward for awareness only (not required to be resolved before this spec proceeds, since they gate future capability additions, not the FR-001–FR-012 scope above):**
- **Data-3 (source spec §26-Data-3).** "Net Revenue" (Revenue minus subsequent `RefundIssued` amounts) has no backing Analytics read model today; only relevant if Business-1 above resolves toward "net" being the more useful default.
- **Data-4 (source spec §26-Data-4).** Cancellation rate/count has no backing Analytics dashboard field today; until built, cancellation questions are declined via the FR-009 "unsupported" path, not approximated from funnel drop-off (which would conflate cancellation with every other form of drop-off).
